02

Current architecture & target

What exists today, end to end, is simulation-only:

MockMarketDataSource | Existing market pipeline (indicators, freshness, strategy, RiskEngine — unchanged) | Human approval + second risk check (Phase 13) | MockBrokerAdapter — delegates to PaperTradingEngine

The target substitutes only the two edges:

REAL MARKET DATA (LiveMarketDataSource) | Existing market pipeline (UNCHANGED) | Existing strategy (UNCHANGED) | Existing RiskEngine (UNCHANGED) | Existing human approval (UNCHANGED) | Existing second risk check (UNCHANGED) | REAL BROKER (RealBrokerAdapter)

Everything between the two edges — strategy, RiskEngine, the approval state machine, the journal, reconciliation, the kill switch — was already built broker-agnostic in Phases 12–13, specifically so this substitution would not require touching them. This phase found one place where that promise doesn't quite hold yet (see §15).

05

Recommended broker: Dhan

Dhan (DhanHQ) is the recommendation, on four specific grounds, not a coin flip:

  1. The Super Order API maps almost exactly onto this project's own Signal model. A Signal already carries stop_price and target_price as one unit alongside the entry. Every other broker researched requires the adapter to place, track, and independently manage 2–3 separate linked orders (entry, stop, target) to replicate what Dhan's single Super Order call already models as one request. This is a real reduction in RealBrokerAdapter complexity, not a marketing point.
  2. Best-documented API of the four, by a clear margin — versioned, changelogged, with dated compliance notices tracking each SEBI deadline. Lower risk of building against stale or ambiguous documentation.
  3. Free trading API removes cost friction from the part of the system that matters most: order placement, modification, cancellation, and status. The optional ₹499/month data API can be deferred — this project can continue using its existing Yahoo-cache path for anything that isn't the final execution decision, exactly as recommended in §6.
  4. Independent prior signal: this project's own CostModel.india_nse_intraday_2026() (Phase 3/4) already assumed Dhan-shaped brokerage costs, before this investigation began. Not decisive on its own, but consistent with everything found here.

Why the others lose:

  • Zerodha has the single best regulatory-philosophy fit (their own product already requires manual confirmation) and is a completely reasonable second choice — but a fixed ₹500/month for data is a real recurring cost against a strategy that is still classified unproven and may execute very few real trades for a long time.
  • Upstox gave the clearest regulatory answer of any broker researched and is the cheapest at low volume — a strong runner-up. It loses only on the order-model fit (no combined entry+stop+target call) and a slightly smaller default WebSocket allowance.
  • Angel One is disqualified primarily on documentation trust: an internal inconsistency between its own published rate-limit table and its newer compliance announcements is exactly the kind of thing that causes a production bug discovered the hard way.

This is a recommendation to design against, not an instruction to sign up. No Dhan account was created and no credentials were requested as part of this research.

06

Live market data

NSE and BSE do not sell real-time data directly to individuals in any simple self-service form — both route real-time/live products through NSE Data & Analytics / BSE's equivalent vendor channel, aimed at institutional and data-vendor clients. VERIFIED

Broker API WebSocket feeds (Dhan/Kite/Upstox/Angel One), by contrast, are genuinely real-time — brokers are exchange members with their own direct connectivity, and the same tick stream powering their own trading terminals is what the API exposes. Typical retail broker-API latency is tens of milliseconds, not colocation-grade but materially live. VERIFIED

Yahoo Finance must not be treated as live trading truth — confirmed, with a specific nuance. Yahoo's own help page lists NSE as "real-time," but independent reports and the unofficial yfinance library both document real-world delay of up to ~15 minutes for NSE-linked symbols — a direct contradiction between Yahoo's documentation and observed behavior. Separately, and regardless of that technical question: Yahoo's Terms of Service explicitly state its data is "for informational purposes only and is not intended for trading or investing purposes," and prohibit redistribution/algorithmic exploitation without written permission. Building any live-decision path on Yahoo data would be a ToS violation independent of latency.

Third-party exchange-authorized vendors (TrueData, Global Datafeeds) offer genuinely exchange-direct real-time ticks, but at ₹1,400–2,800+/month and with a second vendor relationship/contract to manage — more expensive and more integration surface than simply using the execution broker's own feed.

07

Regulatory requirements

The governing rule is SEBI Circular SEBI/HO/MIRSD/MIRSD-PoD/P/CIR/2025/0000013 (Feb 4, 2025), "Safer participation of retail investors in Algorithmic trading," with a further circular (Sept 30, 2025) confirming full mandatory applicability to all brokers from April 1, 2026 — already in force as of this report. VERIFIED, read directly from SEBI's own circular text.

The central question: does human-approval reduce the burden?

Best-supported answer: reduced burden, not zero, and not the same as full algo trading — but SEBI has not explicitly written this exemption down.

SEBI's actual registration trigger is an order-per-second (OPS) rate threshold, not an automation/manual test. The circular never says "a human-approved system is exempt." What it does is register/tag/empanel algorithms that cross a rate threshold (commonly cited at 10 OPS, though the exact number appears only in exchange-issued implementation standards, not SEBI's own circular text). A system where a human clicks approve/reject on every individual order cannot realistically sustain anywhere near that rate — so the heavy machinery (exchange algo registration, Algo-ID, empanelment, Research Analyst registration for opaque logic) is very unlikely to be triggered, as a structural consequence of the design, not a named exemption.

What is NOT reduced: baseline API-channel controls apply regardless of automation status. Per SEBI's own text and confirmed by Zerodha's own compliance documentation ("applies to all Kite Connect users who place orders via the API, regardless of order frequency"), and stated even more explicitly by Upstox ("regardless of whether orders are manual or automated"): static IP whitelisting, a unique non-shared API key, OAuth-based authentication, and mandatory 2FA are required for any order placed via API at all — including a single, human-approved order per day.

  • Static IP: mandatory for order-placement endpoints specifically (not always for read-only/market-data endpoints, per most brokers). VERIFIED
  • Algo-ID / order tagging: required once a strategy crosses the OPS threshold; below it, brokers still track a generic identifier for audit purposes. VERIFIED (mechanism) / exact below-threshold tagging behavior varies by broker documentation quality
  • 2FA + OAuth: mandated by SEBI directly on brokers, for API access generally. VERIFIED
  • Audit trail: SEBI places this obligation on the broker, not the individual retail trader. VERIFIED
  • Broker approval gate: no separate "algo-enabled" approval step was found required below the OPS threshold — typically just a static-IP field in the broker's developer dashboard. VERIFIED (for Dhan/Zerodha/Upstox)
  • Enforcement: documented consequences target brokers (e.g. barred from onboarding new algo-API clients), not individual retail users directly. INFERRED — no SEBI enforcement action against an individual retail API user was found in this research.
  • NSE vs. BSE: both operate under the identical SEBI circular; no evidence of a materially different posture. INFERRED

This should still be confirmed directly with whichever broker's compliance team before any real order is ever placed — brokers, as the parties actually liable to SEBI, may apply internal policy stricter than the letter of the circular. Nothing here should be read as legal advice.

Deployment

The mandatory static-IP requirement (§7) is the deciding factor here, not machine reliability in the abstract. Most Indian residential ISPs (Jio, Airtel, ACT) assign dynamic IPs by default; a static IP add-on costs roughly ₹100–1,000/month depending on ISP and is not always straightforward to obtain on a pure residential plan — it commonly requires a "business" tier. 09

Security model

No real credentials exist anywhere in this project today, and none were created during this research. For when they eventually do:

  • Never in source, never in git. The .gitignore added this phase already excludes .env/*.key/*.pem patterns on principle, before any secret exists.
  • Local encrypted storage, not plaintext. This machine already has pywin32 installed (a transitive dependency), which provides direct access to Windows DPAPI (CryptProtectData/CryptUnprotectData) — OS-native, tied to the logged-in user, zero new dependency. The standard cross-platform keyring package is the alternative if the eventual deployment target isn't Windows (e.g. the VPS from §8, which would more likely be Linux).
  • Refresh/rotation. Every broker researched forces daily token expiry regardless of design choice (§4) — rotation is not optional to build, it's a daily operational fact for all four brokers.
  • Dashboard access. The current dashboard (Phase 13) binds to 127.0.0.1 by default with no authentication — correct for local-only use. If it ever needs to be reachable from off-machine (e.g. approving from a phone while the process runs on a VPS), it needs actual authentication added before that exposure — not built yet, and not needed until real execution is in scope.
  • Revocation. Every broker's developer dashboard supports revoking an API key/app registration directly — the standard "burn it and reissue" path if a credential is ever suspected compromised.

11

LiveMarketDataSource contract

Fits the existing MarketDataSource protocol (live/contracts.py) without modification to the protocol's method names. Reuses OHLCVBar, DataSource.BROKER, DataStatus.LIVE, and FreshnessPolicy exactly as they already exist — all four were built in Phase 12 specifically reserved for this moment, and none needed to change.

One real gap, found by reading the protocol against how a live feed actually behaves: next_bar() -> MarketBarEvent | None currently uses None to mean "the feed has cleanly ended, permanently" — correct for a scripted mock replaying a finite file, meaningless for a live feed that just hasn't completed the next candle yet. The simplest fix that touches nothing else: a real implementation blocks internally (with a timeout) until a bar completes, rather than the protocol growing a third return state. This works cleanly with the existing CLI's tight polling loop and costs nothing architecturally, since a human is already expected to be present for the approval step anyway.

12

Tick vs. candle

Every broker researched streams ticks, not pre-built candles — confirmed directly: Dhan and Upstox both explicitly deliver binary/protobuf tick packets over WebSocket; none of the four offer a "give me a live 1-minute candle" streaming primitive. Building 1m/5m/15m bars from a live feed requires local aggregation.

Tick (price, volume, exchange timestamp) | CandleBuilder (NEW component — nothing in this codebase does tick aggregation today) | OHLCVBar (source=BROKER, status=LIVE — UNCHANGED type) | Existing pipeline (UNCHANGED)

CandleBuilder is genuinely new: open = first tick in the window, high/low = running extremes, close = last tick, volume = summed tick volume, bucketed by the broker's own exchange timestamp (not local receipt time, to avoid skew). It sits entirely inside LiveMarketDataSource, behind the existing protocol — nothing above it changes. This is exactly the "do not create a second market-data processing system" instruction, honored: one OHLCVBar type, one indicator pipeline, one place ticks get turned into bars.

Failure & recovery model

The fail-closed philosophy already built in Phases 12–13 (never repair automatically, always reconcile, halt rather than guess) extends directly — this section is mostly "apply the existing posture," not new design.

ScenarioResponse
Feed disconnectAlready handled — FeedDisconnectedError, fail-closed. Unchanged.
Stale market dataAlready handled — FreshnessPolicy suppresses new signal generation only. Retune the multiplier against real feed latency.
Broker disconnectNew: read-only calls (status/positions) may retry with backoff; place_order() never retries blindly.
Order timeout / accepted-but-response-lostNever resubmit. Query get_order_status()/get_fills() using the broker's own order ID first — a timeout may mean the order landed and only the response was lost.
Order rejectedTerminal, mirrors existing RISK_REJECTED handling. No retry.
Unknown order stateFail closed, flag for manual intervention. Never assume either outcome.
Partial fillGenuine gap: the paper engine assumes full fills only. Modeling partial fills needs a paper/store.py schema extension before real broker support — not attempted this phase.
Duplicate orderPrevented client-side via Signal.stable_id() as an order tag where the broker supports one; reconciliation catches anything that slips through.
Local restartAlready solid — LiveStateStore persistence + _restore_pending_approvals(). Extends without change.
Broker restart/outageTreat as a kill-switch-like halt until reconcile_against_broker() reports clean.
Position/funds mismatchAlready handled — reconcile_against_broker() reports, never repairs. Manual intervention required, matching the existing posture exactly.

Phase 15 implementation plan (not started)

In order, each step keeping the core untouched:

  1. Build CandleBuilder (§12) as an isolated, independently-testable unit — pure tick-in, bar-out, no broker dependency, testable entirely with synthetic ticks.
  2. Build DhanMarketDataSource implementing MarketDataSource, using CandleBuilder internally, against a sandbox/paper Dhan connection first if one exists (REQUIRES BROKER CONFIRMATION whether Dhan offers one).
  3. Build the order-placement translation layer identified in §10/§15 — the piece that turns an approved (Signal, RiskDecision.position_size) pair into a Dhan Super Order request, and turns Dhan's own order/trade responses back into the existing JournalEntry/Position/Trade shapes. This is the one genuinely new piece of business logic in the whole plan.
  4. Build DhanBrokerAdapter completing the contract in §10, including real cancel_order()/modify_order().
  5. Extend reconcile_against_broker()'s existing test suite against Dhan's actual response shapes.
  6. Run the entire existing test suite (412+ tests) unchanged against the new adapters in isolation — if strategy/RiskEngine/approval tests need to change to accommodate a real broker, that itself is a signal the "substitution at the edges" promise broke somewhere.
  7. Only then: a sandboxed, human-approved, paper-executed dry run against real live data with a real (but not yet order-placing) broker connection — observe the approval workflow under real timing pressure before any conversation about real orders.
