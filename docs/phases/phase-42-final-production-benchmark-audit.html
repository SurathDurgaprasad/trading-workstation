Methodology

Against the roadmap's own named checklist: architecture, security, safety, data correctness, freshness, scheduler reliability, provider resilience, database integrity, auditability, learning correctness, dashboard correctness, test coverage, documentation accuracy, git hygiene, operational recovery. Scheduler reliability, provider resilience, and operational recovery were already the entire subject of Phase 39 and re-verified there with dedicated multi-day simulation tests -- re-auditing them here would duplicate that work rather than add to it, so this phase focused its NEW attention on the categories not already covered by a dedicated phase: security, safety-invariant re-verification, database integrity/auditability, a systemic bug-class sweep, and dashboard XSS correctness.

03

Safety & security -- confirmed intact

  • No live order execution path exists anywhere. live.dhan.broker_adapter.DisabledDhanOrderExecutor's three methods (place_order/modify_order/cancel_order) unconditionally raise RealOrderPlacementDisabledError, are not wired into any pipeline, and grep confirms no other place_order/submit_order/execute_order surface exists outside the paper-trading engine and its own tests. The MCP server (mcp_server/server.py) has no order-mutating tool at all, by its own explicit design comment.
  • No hardcoded credentials. A grep for credential-shaped literal assignments across every .py file matched only tests/test_dhan_credential_security.py (a test that itself checks for accidental credential leaks, using fake values).
  • No credential logging. A grep for logger.*(token|password|secret|access_token|client_id) across the whole codebase found zero matches.
  • .env/secrets hygiene. No .db or .env file is tracked by git; .gitignore explicitly excludes them with a comment explaining why, even though none currently exist.
  • No SQL injection surface. Every store uses parameterized ? placeholders except one internal-only f-string table name in paper/store.py's _fetch_all_json, already noqa-flagged and confirmed (by tracing every call site) to only ever receive a hardcoded literal, never external input.
04

Database integrity & auditability -- confirmed intact

  • All 8 store classes (decision_engine, experiments, market_intelligence, paper, predictions, research, scheduler, live.state_store) use the identical sqlite3.connect(path, isolation_level=None) + explicit close() pattern -- no inconsistency, no leaked-connection risk beyond what a short-lived CLI process tolerates trivially, and the one long-running process (schedule loop) already wraps its store in try/finally.
  • The append-only invariant holds everywhere it matters: decisions, predictions (and their evaluations), experiments (and their events), and scan history all have zero UPDATE statements in their stores -- a decision or a resolved prediction's outcome can never be silently rewritten. The only UPDATE statements found anywhere are legitimate single-row LIFECYCLE transitions on genuinely mutable state: a scheduler run's own RUNNING→COMPLETED/FAILED/RECLAIMED status, a paper order/position/journal entry's own open→closed lifecycle, and a pending human-approval's own state machine -- none of these are historical audit records being overwritten, they are live processes updating their own current state, exactly the distinction this project's own established convention draws.
05

Bug found: a fourth naive/aware datetime crash

This session already found and fixed this exact bug CLASS three times (Phase 33 twice, Phase 37 once): this project's own convention is that Yahoo/mock market data produces naive datetimes while real Dhan data has been UTC-aware since Phase 16, and any code that compares or sorts datetimes from both worlds without normalizing first will raise TypeError. A grep sweep for every sorted(...) call keyed on a timestamp-shaped field found one more instance: learning.profitability.compute_profitability_report's chronological sort (added in Phase 41, this session, one phase before this audit) compared PredictionRecord.entry_time directly. entry_time is copied from Signal.generated_at, which is MarketContext.as_of -- naive for an ordinary shadow-run, UTC-aware for one run with --live-source dhan. A single predictions.db accumulated from a mix of both kinds of runs over time (exactly the "long-run operations" scenario Phase 39 cared about) would have genuinely mixed-awareness rows and crash this function.

$ python -c "from datetime import datetime, timezone; sorted([datetime(2024,1,1), datetime(2024,1,2, tzinfo=timezone.utc)])" TypeError: can't compare offset-naive and offset-aware datetimes Fix: chronological = sorted(items, key=lambda item: _normalize_for_sort(item.prediction.entry_time)) (same normalize-to-UTC-aware pattern as market.data_provider._to_timestamp / learning.regime.classify_regime_at / experiments.comparison._naive_utc)

Verified the regression test actually catches the bug (not a false-positive pass) by temporarily reverting the fix and confirming the exact same TypeError reproduces, then restoring it.

09

Known limitations of this audit, stated honestly

  • This was not an exhaustive line-by-line re-read of all ~42 phases' code. It combined targeted grep sweeps for known-risky patterns (credential literals, unparameterized SQL, UPDATE statements, unescaped HTML interpolation, naive/aware datetime comparisons) with spot-checks of the highest-risk modules (order execution, MCP server, dashboard). A genuinely different class of bug this audit did not think to grep for could still exist.
  • The naive/aware fix's real-world mixed-source scenario was not verified against real Dhan data -- this environment has no DHAN_CLIENT_ID/DHAN_ACCESS_TOKEN, so a genuinely mixed real predictions.db (some rows from real --live-source dhan runs, some from Yahoo-only runs) could not be produced and tested end-to-end. The underlying fix is LOCAL/DETERMINISTIC TEST VERIFIED (a direct, deterministic reproduction of the exact tzinfo mix); the live-Dhan half of the scenario remains NOT VERIFIED, honestly, same as every other Dhan-dependent claim in this project's history.
  • Test coverage was reviewed for gaps in the newest modules (Phase 38-41) specifically, not comprehensively re-measured project-wide -- no coverage tool (e.g. coverage.py) was run; this audit's "test coverage" pass was a qualitative read (are there dedicated tests for every new pure function added this session), not a quantitative line-coverage number.
