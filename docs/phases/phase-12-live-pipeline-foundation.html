Live pipeline foundation — Phase 12

A mock feed drives the real deterministic core, end to end

A MarketDataSource protocol, additive source/freshness metadata on the existing OHLCVBar, a fully-scripted deterministic mock feed, a configurable-per-interval fail-closed freshness guard, a human-approval domain state machine, and a pipeline driver that sequences all of it into the unmodified Strategy → RiskEngine → PaperTradingEngine chain — verified byte-for-byte identical to the existing backtester on real AAPL data, and demonstrated end to end against real 1-minute/5-minute NSE data via the CLI. Two real bugs were found and fixed along the way, both through actual data, not synthetic fixtures.

344/345 tests passing (1 pre-existing, unrelated) 0 changes to strategy/baseline.py, risk/engine.py, backtesting/execution.py 2 defects found and fixed via real data 18.5 real bars/sec, 54ms avg latency — ~300x headroom vs. a real 1-minute feed

This is simulated intraday trading infrastructure.
It is NOT connected to a live NSE/BSE feed.
It cannot place real orders.

1Forensic audit

Read directly from the current implementation before any code was written, per this phase's explicit instruction.

QuestionFinding
How does OHLCVBar currently flow through historical replay?YahooFinanceProvider.fetch_ohlcv → OHLCV.from_dataframe → compute_indicator_series (one full-DataFrame pass) → Strategy.generate_signal(indicator_series, i, symbol) — a batch pipeline, not a stream.
How does a bar reach PaperTradingEngine?Two entry points already existed and needed no change: process_bar(symbol, bar: paper.engine.Bar) (fills/exits, with Phase 7A's duplicate/out-of-order protection already built in) and submit_signal(signal) (the real RiskEngine gate, atomic, journaled).
Does PaperSession fit a genuinely streaming, unknown-length feed?No — it requires a fully pre-computed indicator_series DataFrame of known length. This was the one real gap: nothing in the repository could consume bars one at a time from an open-ended source. live/pipeline.py fills exactly this gap without touching paper/session.py.
Is the indicator pipeline interval-aware?Yes already — every function in market/indicators.py is period-parameterized, not hardcoded to daily bars; the only actual gap was a live/streaming SOURCE, not the math.
Smallest safe extension point?Add fields to OHLCVBar (additive, defaulted); add a new live/ package that only calls into process_bar/submit_signal/RiskEngine.evaluate/compute_indicator_series — all pre-existing, public, unmodified.

2Existing components reused, unmodified

  • market.indicators.compute_indicator_series — recomputed on a growing buffer every bar; verified byte-identical to a full-batch computation across all 1,254 real AAPL rows (no divergence found).
  • paper.engine.PaperTradingEngine.process_bar / .submit_signal — the entire duplicate/out-of-order-bar guarantee (Phase 7A) and RiskEngine gate (Phase 4-6) are reused exactly as they already existed.
  • risk.engine.RiskEngine.evaluate — called directly (read-only) for the human-approval flow's FIRST risk check, and again inside submit_signal for the mandatory second check after approval — same engine both times, zero risk logic duplicated.
  • strategy.baseline.TrendMomentumBaseline — used unmodified, still labeled experimental/unproven (Phase 8-11's verdict is unchanged and unrevisited).
  • backtesting.cache.CachedMarketDataProvider, market.data_provider.get_market_data_provider — reused as-is to build the mock feed's historical replay content.
  • paper.reconciliation.reconcile — reused unchanged to verify every new test scenario and the MCP tool's ephemeral simulation.

Every bar can answer, precisely: symbol (carried alongside via MarketBarEvent), timestamp (the bar's own market time), source, status, received_at (stamped by MockMarketDataSource at actual delivery time, not at script-construction time), and source_timestamp (defaults to timestamp, reserved for a future feed where the two can genuinely differ).

6Freshness model

threshold_for(interval) = max(interval_duration * multiplier, minimum_threshold)
default: multiplier=2.0, minimum_threshold=30s

A formula, not a lookup table — generalizes to any interval string without a new entry per interval, and is fully overridable per FreshnessPolicy instance (the live-sim CLI exposes --freshness-multiplier directly). FreshnessPolicy.check() normalizes both the bar timestamp and "now" to naive before comparing — see §13's first bug.

7Mock feed behavior

A fully scripted, deterministic replay engine — nothing wall-clock-dependent unless a test injects a clock. from_cached_history(symbol, interval, period) replays real Yahoo data (re-tagged MOCK/SIMULATED); direct MockScriptEvent lists give exact control over every failure mode: duplicate bars, out-of-order bars, gaps (an absent script entry), delayed bars (received_at stamped far after the bar's own timestamp), and disconnect/reconnect pairs. A bar scripted during a disconnect is LOST (not queued) — the same behavior a real streaming feed has (outages don't replay missed ticks); next_bar() raises FeedDisconnectedError and the script advances, so the very next call resumes from whatever comes after.

8Fail-closed behavior

ConditionResult
Feed disconnectsFeedDisconnectedError caught by the pipeline, surfaced as FEED_DISCONNECTED — no bar processed, no signal generated, pipeline keeps running (doesn't crash) and resumes normally on reconnect

10MCP changes

One new tool: run_mock_live_simulation_tool(symbol, interval, period, max_bars) — replays cached history through the exact same LiveSimPipeline, against a fresh in-memory, ephemeral PaperTradingEngine that is discarded when the call returns. It never opens the persistent paper_trading.db (verified by a test asserting the module-level lazy paper engine stays None), never connects to a real feed or broker, and cannot place a real order. source/status in its response are always "MOCK"/"SIMULATED" — the tool structurally cannot report anything else. Total MCP surface: 12 tools (11 existing + 1). No place_order/execute_trade/live_buy/live_sell tool exists.

The remaining ~97% is the deliberate O(n) full-recompute-per-bar design (compute_indicator_series re-run on the whole accumulated buffer every bar, chosen specifically to avoid writing new incremental-indicator math). 13Bugs discovered and fixed

1. Timezone mismatch in FreshnessPolicy.check() — found via the MCP tool's own test

What: LiveSimPipeline's default clock (datetime.now(timezone.utc), tz-aware) was subtracted directly against historical bar timestamps (tz-naive, per market.data_provider's established convention) inside FreshnessPolicy.check(), raising TypeError: can't subtract offset-naive and offset-aware datetimes. The original docstring said "callers are responsible for normalizing" — the wrong design choice, since it left every caller with a footgun.

Fix: check() now normalizes both timestamps to naive internally (a 2-line _naive() helper, matching paper/engine.py's own established pattern), removing the burden from callers entirely. Two permanent regression tests added (naive-vs-aware in both directions).

2. Test-harness freshness misconfiguration — found via real AAPL parity comparison

What: the paper/backtest parity test's first attempt used a fixed "far future" clock with a freshness multiplier (1000x) smaller than the AAPL series' own 1,825-day span — early bars were correctly flagged stale BY THE FRESHNESS GUARD'S OWN LOGIC relative to that fixed clock, producing a completely different (and far worse) trade sequence than the backtester's. This was not a pipeline defect: it was the freshness guard doing exactly its job against a test that hadn't sized its threshold to the data it was replaying.

Fix: raised the test's multiplier to safely exceed the whole series span. Re-run: exact parity, byte-for-byte, on all real AAPL trades. Documented in the test itself so the same mistake isn't repeated.

No defect was found in strategy/, risk/, backtesting/, or paper/ — both issues were in this phase's own new code and its own test harness, caught by this phase's own real-data testing discipline before being reported as fixed.

15What remains missing for real intraday trading

  • Any actual live/streaming data source — MockMarketDataSource is the only MarketDataSource implementation that exists
  • A real broker adapter of any kind — authentication, live quotes, order placement/modification/cancellation, fills, positions, holdings, funds
  • Live position monitoring against a REAL account, and broker-vs-local reconciliation (today's reconciliation checks internal consistency only, not against an external source of truth)
  • A dashboard — the CLI's text output is a foundation-level demonstration, not the target §13 UI
  • SEBI compliance mechanics (static-IP resolution, Algo-ID tagging, 2FA/session lifecycle) — entirely unaddressed, deliberately, per this phase's scope
  • A UI/API surface for a human to actually call approve_pending()/reject_pending() — the state machine exists and is enforced, but nothing yet presents a pending approval to a person

16Why no real broker was connected

Because this phase's explicit mandate was the foundation, not the integration: build and prove the abstraction (MarketDataSource) against a fully controllable, deterministic mock before writing a single line that depends on network access, credentials, or a specific vendor's API shape. Every failure mode this phase needed to test — duplicate/out-of-order/stale/disconnected data — is far easier to construct and verify deterministically through a scripted mock than through a real feed, and the resulting MarketDataSource contract stays honest about what it actually promises rather than being shaped around one broker's quirks. The prior phase's audit also surfaced a live, current regulatory reason to wait: SEBI's static-IP/Algo-ID/session rules (in force since April 2026) need to be resolved and verified directly with a chosen broker before any real connection is attempted — work that belongs in Phase 15, not folded into this phase's foundation-building scope.

17Phase 13 recommendation

Build live position monitoring and the human-approval surface on top of what this phase proved: unrealized P&L display, stop/target/daily-loss/drawdown/exposure tracking already exist inside Account and just need a presentation layer; a way for a person to actually see and act on a PENDING_HUMAN_APPROVAL signal (even a simple CLI prompt would satisfy the domain model this phase built); and reconciliation logic extended to compare local state against a second, independently-tracked "expected" state (still simulated — a second mock source instance representing "what the broker would say," to rehearse the eventual broker-vs-local check before Phase 15 has to do it for real). No broker, no live feed, no real orders — same posture as this phase, one layer further up the stack.
