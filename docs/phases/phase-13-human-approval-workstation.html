01

Forensic audit

Phase 12 left a simulated bar-driven pipeline (MockMarketDataSource → LiveSimPipeline → PaperTradingEngine) with the domain state for human approval already modeled — a SignalLifecycleState machine reaching PENDING_HUMAN_APPROVAL — but no way for a human to actually act on it: no second risk check, no persistence for a pending decision, no CLI prompt, no kill switch, no broker abstraction, no dashboard. 344 of 345 tests passed (one pre-existing, unrelated Ollama-unavailable failure).

The audit confirmed the one architectural decision this phase depends on: with require_human_approval=True, the transition RISK_APPROVED → EXECUTED is structurally absent from the lifecycle's legal-transition graph. A signal cannot reach execution by any code path except approve_pending() — not a runtime check that could have a bug, a missing edge in the graph itself.

02

Architecture

Ten hops, every one of them either unchanged from an earlier phase or new-and-additive this phase:

MARKET BAR → STRATEGY SIGNAL → RISK CHECK #1 → AI EXPLANATION (optional) → PENDING_HUMAN_APPROVAL → HUMAN APPROVE / REJECT → RISK CHECK #2 → PAPER EXECUTION → POSITION → JOURNAL

Risk check #1 (RiskEngine.evaluate(), no submission) runs the instant a signal is generated, using account state at that moment. Risk check #2 runs again, for real, inside approve_pending() — against whatever the account looks like at the moment a human decides, which may no longer be the same account. Nothing about the human's decision is trusted to still be valid; it is re-derived.

New this phase

  • live/state_store.py — LiveStateStore, a durable audit trail for every signal that ever reached PENDING_HUMAN_APPROVAL, plus the kill switch.
  • live/broker.py — a BrokerAdapter protocol and MockBrokerAdapter, delegating entirely to the existing PaperTradingEngine.
  • live/broker_reconciliation.py — compares our expected state against the (mock) broker's, never repairs.
  • live/workstation.py — the single access layer for the persistent paper-live account and approval state, shared by the MCP server and the dashboard so neither re-implements it.
  • main.py paper-live — the operator-facing CLI.
  • dashboard/app.py — a minimal local web view over the same state.

Approval lifecycle

live/approval.py's SignalLifecycleState graph, extended this phase with expiry:

StateReachable fromMeaning

RISK_APPROVEDSIGNAL_GENERATEDRisk check #1 passed.
RISK_REJECTEDRISK_APPROVED, HUMAN_APPROVEDTerminal. Either check can reject.

PENDING_HUMAN_APPROVALRISK_APPROVED, AI_EXPLAINEDWaiting on a human. Persisted.
APPROVAL_EXPIREDPENDING_HUMAN_APPROVALTerminal. approval_timeout_seconds elapsed, no decision.
HUMAN_APPROVEDPENDING_HUMAN_APPROVALHuman said yes — risk check #2 has not run yet.
HUMAN_REJECTEDPENDING_HUMAN_APPROVALTerminal.
EXECUTEDHUMAN_APPROVEDTerminal. Only reachable after BOTH risk checks passed.

The HUMAN_APPROVED → RISK_REJECTED edge exists because a human's yes is not the final word — the account may have moved between the two checks (see §13). RISK_APPROVED → EXECUTED is not in this graph when human approval is required. It cannot be reached by construction.

04

Mock broker adapter

BrokerAdapter is a six-method protocol (submit_order, cancel_order, order_status, list_fills, list_positions, get_funds) shaped like what a real broker integration would eventually implement. MockBrokerAdapter is the proof that the abstraction costs nothing: every method is a one-line delegation into the existing PaperTradingEngine — no execution logic is duplicated anywhere.

cancel_order raises NotImplementedError with an honest explanation: the paper engine has no CANCELLED order state today. That is a documented Phase 6 scope limit, not something faked to make the interface look complete.

05

Reconciliation

reconcile_against_broker(engine, broker) reuses Phase 6's ReconciliationReport/ReconciliationIssue types directly. It matches positions by symbol and trades by content — (symbol, entry, exit, quantity, exit_reason) — deliberately not by our own internal IDs, since a real broker would never share our ID scheme.

CheckDetects
missing_position_at_brokerWe think a position is open; the broker disagrees.
unexpected_position_at_brokerThe broker shows a position we never opened.
quantity_mismatch / price_mismatchSame position, different numbers.
cash_mismatchAccount cash disagrees.
trade_missing_at_broker / duplicate_trade_at_brokerTrade history diverges.

It never repairs anything it finds — a discrepancy is reported, not silently fixed.

Kill switch

A single row in LiveStateStore, checked before every new signal is allowed to reach an order — in both auto-execute and human-approval modes.

Activate

Reset
python main.py paper-live --reset-kill-switch
Survives
Process restart — it's a SQLite row, not in-memory state.
Does NOT
Touch existing open positions or already-pending approvals. It blocks new ones only.

An explicit reset. It never clears itself.

08

The paper-live CLI

python main.py paper-live --symbol RELIANCE.NS --interval 1m --period 1d — the primary operator interface. Verified end to end against real cached AAPL data in three modes: interactive approval, --auto-approve/--auto-reject for scripted runs, and the kill-switch activate/blocked/reset cycle.

SIGNAL DETECTED Signal ID: 4b09f24e86b2 Symbol: AAPL Direction: LONG Entry: 165.30 Stop: 159.70 Target: 176.51 Quantity: 89 RISK: APPROVED (risk check #1 passed -- a second, independent check runs again at the moment of your decision) APPROVE [Y] / REJECT [N]: Y -> APPROVED (APPROVED_PENDING)

The AI-explanation step (agents.signal_explainer, unchanged from Phase 4.5) is attempted by default and silently skipped — never blocking the prompt — whenever Ollama is unreachable.

09

Local dashboard

python main.py dashboard — a Starlette app (no new dependency; Starlette/uvicorn/Jinja2/httpx already ship as transitive deps of the mcp package), bound to 127.0.0.1 by default. Seven sections: MARKET, SIGNALS / PENDING APPROVAL, POSITIONS, ACCOUNT, RISK, JOURNAL, plus a kill-switch control.

Every route handler calls straight into live/workstation.py — the exact same functions the MCP tools and, transitively, the CLI's domain layer use. Approve/Reject buttons post to routes that call approve_pending_signal()/reject_pending_signal(); no route computes a risk decision, a signal, or an account balance itself. Verified live in-browser: seeded a real pending AAPL signal, clicked APPROVE, watched it move into the journal as APPROVED_PENDING.

The dashboard deliberately never calls process_next() — it doesn't advance the market. That stays the CLI's job, so two processes never race to drive the same feed.

11

AI boundary

Unchanged in kind from every prior phase, re-verified here: agents.signal_explainer.explain_signal() returns a SignalExplanation with exactly three fields — supporting evidence, contradicting evidence, narrative. No field exists for entry, stop, target, quantity, or approval status. The type system makes override impossible, not a prompt instruction the model could ignore.

The AI step is never on the critical path: _try_ai_explain() wraps the entire call in a broad exception handler and logs-and-continues on any failure, including Ollama being completely absent.

12

Persistence

LiveStateStore opens its own SQLite connection, to its own file, with explicit BEGIN/COMMIT transactions — never Postgres, Redis, or Kafka, and never a modification to paper/store.py's schema. Two tables: pending_approvals (one row per signal ever sent to PENDING_HUMAN_APPROVAL, updated in place as its lifecycle advances — the durable audit trail) and kill_switch (one row, survives restart).

The audit trail per signal: signal_id, strategy_version, risk_config_version, requested and approved quantity, the human's decision and its reason, decision timestamp, and the final execution result.

14

Restart behavior

On construction, LiveSimPipeline calls _restore_pending_approvals(), rebuilding every PENDING_HUMAN_APPROVAL signal's in-memory SignalLifecycle from LiveStateStore.list_pending(). A pending approval created, then the process killed, then a fresh process started against the same DB file: the signal is still there, still approvable, still subject to its original expiry.

15

Idempotency & the critical security test

approve_pending(self, signal_id, *, reason=None) — that is the entire signature. No quantity, stop, target, or price parameter exists to override. A dedicated test calls approve_pending(object(), signal_id="x", quantity=100_000, stop=0, target=999_999) directly and asserts it raises TypeError — the attack is structurally impossible, not merely rejected at runtime.

Every action returns a typed outcome rather than raising or silently no-op'ing: APPROVED | REJECTED | ALREADY_DECIDED | EXPIRED | NOT_FOUND | KILL_SWITCH_ACTIVE. Approving twice, rejecting an already-executed signal, or approving an unknown ID all report cleanly.

Bugs discovered & fixed

Enum serialized via str() instead of .value production bug — fixed

Found via the restart test on real AAPL data. _serialize_history wrote "SignalLifecycleState.SIGNAL_GENERATED" instead of "SIGNAL_GENERATED", which then failed to parse back on restore. Fixed in live/state_store.py; a permanent regression test now round-trips enum states through save/restore.

Test invariant too coarse for same-bar close-then-reopen test bug — not production

test_position_already_open_prevents_a_second_pending_approval asserted no second pending approval could occur while checking position state only at the start of each loop iteration. Traced it: a single process_next() call can close the existing position (its stop/target fills) and generate a fresh, independent signal that legitimately clears risk check #1 in the same call. Fixed the invariant to check whether a trade actually closed within that same bar before treating a new pending approval as a violation.

Synthetic flat-price bars never satisfy the strategy test bug — not production

TrendMomentumBaseline needs SMA20 > SMA50, which a constant-price mock series never produces. Every new test needing a real signal switched to a shared real_aapl_mock_script() helper built from cached AAPL history.

Fixed clock vs. multi-year real data test bug — not production

A fixed 2026 clock against 2021–2026 AAPL bars, under the default freshness multiplier, correctly-but-inconveniently flagged early bars stale. Fixed with a large test-only FreshnessPolicy multiplier.

Windows PermissionError on manual temp-dir cleanup test bug — not production

Unclosed sqlite3 connections inside a manually-managed tempfile.TemporaryDirectory() block left Windows unable to delete the directory. Switched to pytest's tmp_path fixture throughout.

Starlette TestClient cross-thread SQLite reuse test-only artifact

TestClient dispatches each call through a new anyio thread-portal, so a cached sqlite3 connection opened on one call fails on the next ("created in thread X, this is thread Y"). Confirmed this cannot happen in real deployment — the CLI, MCP server, and dashboard are always separate single-threaded OS processes — and verified the dashboard against a genuine uvicorn process instead (8.8ms mean, no error). Dashboard tests disable the engine cache locally so each call opens its own connection to the same file, exactly reproducing the real multi-process shape.

What remains before real broker integration

  • SEBI's algo-trading framework (in force since April 1, 2026): static-IP whitelisting, an exchange-assigned Algo-ID, mandatory 2FA/session expiry. A hard blocker for casual home-network live trading, independent of any code in this repository.
  • A real BrokerAdapter implementation (e.g. DhanBrokerAdapter) — not started, not attempted this phase.
  • A real, licensed market-data feed with genuine LIVE status (everything today is MOCK/SIMULATED replaying cached history).
  • Credential storage and the operational discipline around it — out of scope until a broker exists to hold credentials for.
  • The strategy itself remains classified C — no evidence of a durable edge (Phase 8–11). Nothing in this phase changed that, and nothing here was intended to.
21

Recommendation

The human-approval workstation is now reliable enough to operate against simulated data: CLI, dashboard, and MCP surfaces all read and act through one shared, tested domain layer; every fail-closed scenario the spec named has a passing test; the critical security property (no client-suppliable execution override) is proven structurally, not just behaviorally.

Do not start a Phase 14/15 broker integration until the SEBI compliance blocker above has an actual resolution path outside this codebase — more simulated infrastructure will not change that constraint. The next useful increment, if any, is operating this exact system against live but still-paper-executed market data, purely to observe the approval workflow under real timing pressure before any conversation about real capital.
