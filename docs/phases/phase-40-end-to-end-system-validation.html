Scope

In scope: auditing the full pipeline for cross-stage failure isolation and restart survivability; fixing any real gap found; a new test file adding exactly the coverage that did not already exist (evaluate-stage failure injection, a genuine restart-across-process-boundary test, a full-stack dashboard-renders-what-shadow-run-wrote check).

Explicitly out of scope: re-proving per-stage correctness tests/test_shadow_run.py (Phase 27), the scanner/decision/prediction test suites, and Phase 39's scheduler tests already cover in depth -- this phase reads that coverage first and only adds what is missing, per this project's own "prefer extension over duplication" convention.

03

The bug found

The decide stage's per-symbol loop in run_shadow_run_command already wraps each symbol in its own try/except -- one symbol's failure was already proven (Phase 27) not to abort the rest of the universe. The EVALUATE stage had no equivalent: both run_evaluate_command's loop and shadow-run's own [3/4] evaluate loop called evaluate_prediction for each pending prediction with no per-item try/except. evaluate_prediction itself already catches MarketDataError internally (returning an INSUFFICIENT_DATA evaluation), but ANY other exception -- an unexpected bug, a transient I/O error, a malformed row -- would propagate out of the loop, aborting evaluation of every OTHER pending prediction in the same batch and, in shadow-run's case, skipping the [4/4] learning summary entirely. For a scheduled evaluate_and_learn slot with many pending predictions, one bad one could silently cost every other prediction its update for that tick.

04

What was built

Both evaluate loops, before: for prediction in pending: evaluation = evaluate_prediction(prediction, ...) # an exception HERE aborted the whole batch store.save_evaluation(evaluation) Both evaluate loops, after (same posture as the existing decide-stage per-symbol loop): for prediction in pending: try: evaluation = evaluate_prediction(prediction, ...) store.save_evaluation(evaluation) except Exception as exc: logger.warning(...); print(f"... FAILED ... {exc}") # continues to the next prediction; the summary/learning step below still runs

Tests

07

Safety

  • The fix only adds error isolation (try/except + logging) around already-existing calls -- no new write path, no new network call, no change to what gets persisted for a successfully-evaluated prediction.
  • No code path added or touched here places an order, real or paper -- every new test asserts "No real or paper order was placed" text is still present in shadow-run's output.
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
08

Known limitations, stated honestly

  • Failure injection was exercised at the decide and evaluate stages only. Research-stage (news/sector provider) and prediction-store-write failures were not separately fault-injected in this pass -- the decide-stage isolation (which wraps research + decide + predict together in one try/except per symbol, per Phase 27's original design) already covers a research-provider failure the same way it covers a decide failure, so no separate test was added; this is noted rather than assumed.
  • The restart test simulates a restart by using fresh Python objects, not fresh OS processes. Every store already opens its own SQLite connection per instantiation and nothing in this codebase relies on cross-invocation Python state, so this is equivalent in practice, but a literal subprocess-boundary test was not run.
  • No consecutive-failure threshold for the evaluate loop (matching Phase 39's identical, deliberate choice for the scheduler loop) -- if every pending prediction fails for the same persistent reason, the loop will report every one as FAILED rather than giving up early. Visible in the output, not self-terminating.
