02

Scope and safety rules

Phase 16's mandate was narrow and explicit: verify the already-built Dhan integration against the real service, never build real order execution, never bypass human approval, never let strategy or risk logic change. Every session began with the same non-negotiable pre-flight: the six-test test_dhan_no_real_orders.py suite had to pass before any network call, and every credential check displayed presence only, never a value.

Real-service testing was deliberately conservative throughout: a single controlled connection attempt per session (max_reconnect_attempts=0 where the objective was diagnostic isolation), explicit market-session checks before connecting, and an explicit stop-and-report posture the moment anything looked like a rate limit, an account block, or a timestamp contradiction — rather than retrying or guessing.

03

Bugs found and fixed, in the order discovered

1. Dhan /holdings undocumented empty-state behavior FIXED — b6c8936

A real account with zero holdings makes /holdings return HTTP 500 with errorCode: DH-1111 instead of 200 + [] — not in Dhan's documented error tables. get_holdings() now treats that specific shape as an empty list; any other error still raises.

2. Optimistic CONNECTED-before-handshake race FIXED — b6c8936

_connect() used to declare CONNECTED and send the subscribe message the instant the background thread started, not once the handshake had actually succeeded. A real connection that closed immediately crashed subscribe() with a raw WebSocketConnectionClosedException. Fixed with a genuine on_open signal from the transport layer.

3. Reconnect storm — the client ID was rate-limited by Dhan FIXED — 2d7d813

A real connection failure fires both on_error and on_close (each from its own thread), and a send failure could report independently — each call triggered its own reconnect attempt with no deduplication. Under genuine concurrency this multiplied into dozens of real connection attempts within ~15 seconds, and Dhan's server responded with HTTP 429 "... client id is blocked". A deeper cause was found alongside it: the retry counter reset to 0 on every successful open, so a rapidly flapping connection never actually reached the configured bound — only Dhan's own rate limiter stopped the storm, not this project's code. Fixed with generation-tagged, lock-protected reconnect claiming (exactly one reconnect per real failure) and a stability-gated retry-counter reset (only resets after a connection has been open for min_stable_connection_seconds, default 10s).

4. Three further hardening bugs, found by offline code review (no live testing) FIXED — b8d36bb

  • FAILED-recovery retry-budget bug: subscribe() reconnecting from a permanent FAILED state called _connect() directly, bypassing the path that resets the retry counter — a manual resubscribe after a permanent failure could silently fail again after zero real retries.
  • close()/reconnect orphan-connection race: close() mutated state and read the transport reference without the lock used everywhere else; an in-flight reconnect could race past a concurrent close() and open an untracked WebSocket the caller believed was closed.
  • Credential redaction (defense-in-depth): no actual leak was found — the pinned websocket-client version's exception paths were checked directly and never embed the request URL — but every string reaching _last_disconnect_reason is now defensively redacted anyway.

Verified with 6 new tests including a genuine multi-threaded stress test reproducing the real race, run repeatedly with no flakiness.

5. Dhan WebSocket "Last Trade Time" timezone bug FIXED — ba12d3e

Dhan's documented "epoch" field, decoded the standard way, read back the current IST wall clock, not UTC — off by very nearly 5 hours 30 minutes. This was cross-checked against Dhan's own real HTTP Date header from an earlier session to confirm this project's local clock was itself accurate (ruling out a local-clock artifact). Uncorrected, this silently broke FreshnessPolicy for every real Dhan bar: a bar timestamped ~5.5 hours in the future makes age = now − bar_timestamp negative, which is always ≤ any positive threshold, so every real bar was always judged "fresh" regardless of actual staleness. Fixed by reinterpreting the decoded wall-clock digits as IST before converting to the genuinely correct UTC instant. Re-verified in a later session across 589 real packets: the fix holds — only the much smaller, independently-corroborated ~2-minute Dhan-server/local clock skew remained, never the original ~5.5-hour error.

The fix in ba12d3e was re-validated in a later session against 589 real packets in a single connection. Every packet's decoded age fell in a tight, stable band (roughly −112s to −122s, mean −121.6s) — consistent with the same small, already-documented Dhan-server/local clock skew, and nowhere near the ~19,800 second (5.5 hour) magnitude the original bug produced. 07

Reconnect state machine, final form

The final implementation funnels every way a connection can be discovered lost — on_error, on_close, a send failure, a server-sent Disconnect packet — through one generation-tagged, lock-protected entry point, so exactly one reconnect is claimed per real failure. The retry counter only resets after a connection has been stable for a configurable minimum duration, not merely opened, so a flapping connection correctly accumulates attempts toward the bound instead of resetting on every brief open. close() and an in-flight reconnect are mutually exclusive under the same lock, eliminating the orphan-connection race found during the offline hardening pass. This was verified with deterministic tests, including a genuine multi-threaded stress test, run repeatedly with consistent results (state: LOCAL/CONCURRENCY VERIFIED for the reconnect logic itself; the bounded single-attempt behavior was additionally observed against the real service in every live session, with no reconnect storm recurring).

09

What was not naturally observed

No natural trading signal occurred against real market data in any Phase 16 session. RELIANCE moved only about −0.13% over the longest observation window — a legitimate, unremarkable market outcome, not a code gap. Strategy parameters were never changed to force a signal, per the phase's explicit instruction.

Consequently: Signal generation from real data is NOT NATURALLY OBSERVED. RiskEngine, human approval, and paper execution reached from a naturally-occurring real signal are each NOT NATURALLY OBSERVED — these three stages are exercised only by the existing deterministic test suite (test_dhan_pipeline_integration.py, test_dhan_no_real_orders.py), which is real, valuable evidence, but is explicitly and deliberately not the same claim as "real-service verified."

Security & credential audit

  • No secret-shaped string found anywhere in the Phase 16 diff or in the full patch text of all four commits.
  • .env confirmed gitignored and untracked in every session; .env.example contains placeholder names only.
  • Credential values were never displayed, logged, or printed — every session's diagnostics checked presence and length only.
  • DhanCredentials.__repr__ is hardcoded masked; _redact_secret() defensively strips the raw token from any disconnect-reason text before it is stored or logged.
  • Order-placement/modify/cancel code paths remain structurally absent — DisabledDhanOrderExecutor is defined but never imported by any production caller (verified by direct grep, not just tests).
