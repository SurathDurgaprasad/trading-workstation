02

Reconciliation

Most of what Phase 32 asks for was already real, working infrastructure by the time this phase started: reconnect behavior and stale-feed detection live in DhanMarketDataSource/FreshnessPolicy (Phase 15-17), market-session handling in live.dhan.market_session (Phase 15), and the live-vs-historical labeling mechanism itself in Phase 31's get_market_context(live_snapshot_provider=...). What was genuinely missing: that mechanism only reached ONE symbol at a time (size/predict); a whole-watchlist shadow-run pass had no way to request a live overlay at all, and even when a decision DID carry live-vs-historical provenance, nothing displayed it anywhere a human would actually look.

03

What was built

shadow-run --live-source dhan 1. ONE adapter built for the whole run (main._build_live_snapshot_provider, unchanged from Phase 31 -- same credential loading, same Dhan adapter) 2. passed into get_market_context() for EVERY candidate in the loop 3. closed exactly once, after the loop, before the evaluate/learn tail schedule tick/loop --live-source dhan --resilient -> threaded through to shadow-run's own --live-source flag, same as --resilient /intelligence dashboard -> new "Data Source/Status" column: decision.market_context.data_source/ data_status when present, an honest "n/a" when the decision has no market_context at all (e.g. from standalone `decide`)

shadow-run's header now also prints the current market session (reusing current_market_session() verbatim, informational only -- it does not gate whether the run proceeds) and whether a live overlay is active, so an operator watching scheduled runs can see at a glance whether decisions were informed by live or historical data.

Tests

4 new tests: shadow-run's market-session/live-overlay header lines, a full --live-source dhan run with a fake adapter proving every candidate gets the overlay and the adapter is closed exactly once, and two dashboard tests (data source/status shown when present, an honest "n/a" when absent). 06

Safety

  • No new order-placement or broker-mutation path -- --live-source dhan on shadow-run reuses the exact same read-only get_snapshot() call Phase 31/18 already established.
  • The adapter is guaranteed closed after the loop regardless of individual candidate failures (the existing per-candidate try/except already isolates those; nothing new escapes the loop).
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
07

Known limitations, stated honestly

  • A real Dhan live overlay across a watchlist has not been exercised -- same honest gap as Phase 31, for the same reason (no credentials in this environment).
  • Market session is informational only. shadow-run still runs regardless of session state (CLOSED included) -- this phase does not gate execution on market hours, since a shadow-run against historical data is meaningful even when markets are closed.
  • The dashboard's "no decision recorded" row still lacks a Data Source/Status cell entry beyond "n/a". Correct behavior, not a gap -- there is no decision to describe.
