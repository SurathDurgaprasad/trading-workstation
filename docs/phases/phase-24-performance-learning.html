Phase 24 — Performance Learning System

Read Only, By Design

A new learning/ package turns Phase 23's prediction history into strategy comparison, market-regime performance, a simple confidence-calibration check, and signal-quality stats — a pure report over existing data. The roadmap's own Phase 24 rule ("No automatic strategy modification without Versioning/Evaluation/Rollback/Audit Trail") is honored the simplest possible way: this phase writes to no configuration anywhere, ever.

02

Scope

In scope: read-only analysis over Phase 23's predictions/ + Phase 21's decision_engine/ history — strategy comparison (by config version), market regime performance (at each prediction's entry), a simple confidence-calibration check (composite-score median split), and signal-quality aggregates (MFE/MAE, already stored by Phase 23).

Explicitly out of scope: any write to decision_engine.config.DecisionConfig, risk.config.RiskConfig, or any other configuration — the roadmap's own Phase 24 rule forbids automatic strategy modification without versioning/evaluation/rollback/audit trail this project has no path for yet. Also out of scope: Experiment Tracking and Model Comparison in any literal sense (see §04), and any order, real or paper.

03

What was built

learning/ models.py StrategyPerformance, RegimePerformance, CalibrationBucket, SignalQualityReport, LearningReport regime.py MarketRegime, classify_regime_at() -- reuses Phase 9's own SMA200 broad-trend convention analysis.py EvaluatedPrediction + four pure analysis functions + build_learning_report()

main.py learn joins predictions.store.PredictionStore (every prediction + its latest evaluation) with decision_engine.store.DecisionStore (each prediction's originating Decision, for config_version/composite_score), builds the EvaluatedPrediction list, and prints the resulting report. No new persisted store: this is a stateless report over two existing databases, the same "preview only" posture Phase 22's size command already established.

Honest interpretation of six roadmap features

05

What was reused, not rewritten

  • strategy.regime_filters.BROAD_TREND_SMA_PERIOD (200, from Phase 9) and market.indicators.compute_sma — the exact same broad-trend convention, not a new regime methodology.
  • The win-rate/average-return/profit-factor formula already proven in predictions.tracker.summarize_predictions — a resolved LONG-only prediction's actual_return sign is its own win/loss signal by construction (risk.sizing.build_signal_for_buy's stop < entry < target ordering). Factored into one local helper (learning/analysis.py's _resolution_stats) reused by all three functions that need it, rather than three separately-drifting copies -- deliberately NOT imported from predictions/tracker.py, since that would invert the intended dependency direction (learning/ depends on predictions/, never the reverse).
  • predictions.store.PredictionStore / decision_engine.store.DecisionStore (Phase 23 / Phase 21) — read unchanged; learning/ itself never touches SQLite directly, keeping it decoupled and independently testable with plain in-memory data.
  • backtesting.cache.CachedMarketDataProvider — wired at the CLI layer exactly as backtest/scan/evaluate already do.
06

Self-audit: adversarial edge cases checked

  • Division by zero with zero or one resolved predictions. _resolution_stats and compute_signal_quality both return None for every metric on empty input — covered by dedicated empty-input tests for every one of the four analysis functions and build_learning_report itself.
  • Median split with an odd item count. Explicitly decided and documented in code: the exact middle score becomes the threshold, and that middle item itself lands in the "at or below" bucket (not "above") — verified directly rather than left ambiguous (test_confidence_calibration_odd_count_median_goes_to_at_or_below), plus a companion even-count test proving the two-middle-average threshold.
  • A prediction whose decision_id doesn't resolve to any Decision. Degrades gracefully to decision=None on EvaluatedPrediction rather than crashing the join. Decided and tested precisely which analyses that excludes it from: strategy_comparison and confidence_calibration both skip it (they need Decision data), while signal_quality still includes it (it only needs PredictionEvaluation, which came from Phase 23 independently of any Decision lookup) — both boundaries have their own dedicated test.
  • A BUY Decision with scanner_evidence=None. Attempted directly in a test and found impossible to even construct — Phase 21's own Decision model_validator already forbids it. The calibration code's defensive scanner_evidence is not None check is accordingly dead code in practice, kept anyway as cheap, harmless defense-in-depth; the test was corrected to check only the reachable case (a missing Decision entirely) rather than assert an unreachable one.
  • Zero writes to any configuration. Verified directly with a fresh grep across learning/ for DecisionConfig/RiskConfig — both names appear only in comments and docstrings, never imported or assigned.

Tests

27 new tests (verified via pytest --collect-only): 5 in test_learning_regime.py (uptrend/downtrend/insufficient-history/fetch-failure/as-of-boundary), 13 in test_learning_analysis.py (every analysis function's grouping and edge-case behavior, including the odd/even median-split cases and the no-decision exclusion boundary), 5 in test_learning_models.py (basic shape/None-safety of each model), and 4 CLI tests (arg parsing, a zero-predictions run, and one end-to-end run composing real PredictionStore+DecisionStore data through to a populated report, with the market-data provider faked out and CachedMarketDataProvider replaced with an identity pass-through so no data/market/ cache file is ever written by the test suite -- verified directly via git status after the run). No real network or Ollama call anywhere in the unit suite. Full regression: 774 passed, 0 failed.

08

Known limitations, stated honestly

  • Small-sample noise is not addressed. With few predictions, a median split or per-config comparison can be dominated by one or two outliers; no significance testing or minimum-sample gating is applied. Reading a learn report as a strong signal from a handful of predictions would be a misuse of it, not a defect in it.
  • Regime classification is retroactive and independent of Phase 23. PredictionRecord does not store a regime label at prediction time; learning/regime.py reclassifies from historical data at analysis time instead, keeping Phase 23's model untouched at the cost of a second data fetch per prediction when learn runs.
  • No automatic re-running. Like evaluate, learn must be invoked manually (or by an external scheduler); this phase adds no background loop.
