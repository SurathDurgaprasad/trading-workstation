Phase 37 — Experiment Tracking

A Named Window, Not Just a Config Hash

Every tunable config in this project (DecisionConfig/ScannerConfig/RiskConfig) already has a deterministic version_id() hash -- what was missing was a REGISTRY of which versions were deliberately tried, when, and why, and a comparison that isolates each experiment to its OWN dataset/time boundary rather than a config version's lifetime aggregate. A new experiments/ package plus python main.py experiment start|end|list|compare adds exactly that, reusing the config versioning and win-rate math that already existed.

02

Scope

In scope: an Experiment registry (name, description, config type/version, start time), an append-only event log (STARTED/ENDED/NOTE, current status always DERIVED from the latest event, never a stored mutable field), and a comparison that filters predictions to each experiment's OWN [started_at, ended_at or now) window AND matching config_version before computing win rate/average return/profit factor -- reusing learning.analysis's exact formula, never re-derived.

Explicitly out of scope: tracking a NON-default config (e.g. a custom scanner weight set) -- experiment start records whichever config's CURRENT DEFAULT version_id() is in effect for the chosen --config-type; any automatic promotion/rollback of a "winning" experiment (that is Phase 38's explicit job, and the roadmap is explicit that promotion requires evidence thresholds this phase does not attempt to define).

03

What was built

python main.py experiment start --name "..." --config-type decision_engine --description "..." -> records DecisionConfig().version_id() (the REAL, existing, unmodified hash) + now() as started_at python main.py experiment end --experiment-id ... --note "..." -> appends an ENDED event; refuses if already ended; NEVER rewrites the original registration python main.py experiment compare -> for each registered experiment: window = [experiment.started_at, ended_at-or-now) predictions = { p : p.decision.config_version == experiment.config_version AND p.created_at in window } win_rate/avg_return/profit_factor = learning.analysis's own, unmodified formula over `predictions`

Same two-table append-only pattern predictions/store.py already established (Phase 23): experiments written once, experiment_events appended-to, current status derived by reading the latest event -- never a mutable "status" column.

06

Safety

  • Purely a registry and a read-only comparison -- no code path here changes DecisionConfig/ScannerConfig/RiskConfig, places an order, or alters any decision label.
  • Append-only, matching every other store in this project -- experiment end never rewrites the original registration, only appends an event; hasattr-verified no update_experiment/update_event method exists.
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
07

Known limitations, stated honestly

  • Only the CURRENT DEFAULT config's version can be registered via the CLI. There is no way yet to say "start an experiment for THIS specific non-default config" from the command line -- a real, named gap, not an oversight.
  • No automated promotion. Comparing two experiments' win rates is entirely a human-read report; nothing here decides "config B is better, switch to it" -- that judgment, and any resulting config change, remains manual, exactly as the roadmap requires until Phase 38's own evidence-threshold framework exists.
  • Two experiments started for the same config_type at overlapping times, without changing the underlying config, will double-count the same predictions in both. Nothing currently warns about overlapping experiment windows -- a real, minor gap for a future pass.
