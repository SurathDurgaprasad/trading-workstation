02

Reconciliation

The authoritative roadmap (PROJECT_GOAL_AND_ROADMAP.md) explicitly marks everything past Phase 27 as "Future Expansion... not automatically approved, requires separate architecture review." That review was supplied directly: a detailed, numbered specification for Phase 28 (scheduling abstraction, market-session/holiday awareness, idempotent run identity, overlap prevention, restart recovery, graceful shutdown, no default infinite loop) was given as an explicit operator instruction, which this phase implements as scoped.

Phase 27's own report named the exact gap this phase closes: "No built-in scheduler. Deliberately not built — the user's own cron/Task Scheduler pointed at python main.py shadow-run ... is sufficient infrastructure." That remained true for an EXTERNAL trigger, but the operator's Phase 28 spec asks for more: idempotency, overlap prevention, and restart recovery that a bare cron entry calling shadow-run repeatedly does not provide on its own (a cron job has no way to know "did today's pre-market run already happen" or "is another instance still running").

03

Scope

In scope: a configurable schedule (5 default slots matching the roadmap's own pre-market/market-open/intraday/pre-close/post-market concepts, YAML-overridable), an on-disk run-history store that doubles as an overlap-prevention lock and a restart-recovery mechanism, a schedule tick (one check-and-maybe-run cycle, safe to call from an external cron) and schedule loop (explicit, opt-in continuous polling) CLI, and a schedule status read-only audit view.

Explicitly out of scope: any new market-data source, any change to shadow-run/evaluate/learn's own logic (the scheduler calls them exactly as they already exist), and real NSE/BSE holiday-calendar integration (holidays are a plain user-supplied date list — see §10).

Reuse, not duplication

  • scheduler.runner._execute_slot calls main.run_shadow_run_command / main.run_evaluate_command / main.run_learn_command directly (via a synthetic argparse.Namespace built with the existing parse_args), exactly the same functions the standalone CLI commands call — zero reimplementation of scan/research/decide/predict/evaluate/learn wiring.

06

Bugs found and fixed by self-audit

1. `finished_at` silently used real wall-clock instead of the tick's own injected `now`

Caught by a failing test, not by inspection: run_tick called run_store.finish_run(...) without an explicit finished_at, so it defaulted to datetime.now(timezone.utc) — the REAL current time — even when the caller had injected a synthetic now (the --now dry-run flag, or a test). This made the intraday slot's 60-minute re-trigger frequency check compare against the wrong reference point, and made the documented --now "what would run at 09:20 IST" feature silently inconsistent. Fixed by passing finished_at=now_utc explicitly in both the success and failure paths, with a regression test (test_finished_at_is_anchored_to_the_injected_now_not_real_wall_clock) pinning the fix.

2. A TOCTOU race could let two scheduler processes both start an overlapping run

Found by re-reading the lock-acquisition code adversarially (not by a failing test): the original design checked active_lock() and then, as a SEPARATE call, start_run() — two operations with a gap between them. Two scheduler processes racing on the same run-db (e.g. an operator accidentally running both schedule loop and a cron-triggered schedule tick against one database) could both observe "no lock held" before either had inserted its own row, and both then execute overlapping shadow-runs — a direct violation of the roadmap's "prevent overlapping runs" requirement. Fixed by adding SchedulerRunStore.try_start_run, an atomic check-then-insert inside one BEGIN IMMEDIATE transaction, which SQLite serializes at the file-lock level. Verified with a genuine concurrency test: two separate SQLite connections (simulating two OS processes) racing via a threading.Barrier, asserting exactly one wins.

09

Safety

  • Every scheduler code path routes through the existing, unchanged run_shadow_run_command/run_evaluate_command/run_learn_command — no new order-placement, broker, or paper-mutation code path exists anywhere in scheduler/.
  • schedule loop is never the default; only schedule tick (one cycle, exits) and schedule status (read-only) are, satisfying "no infinite loop by default CLI accident."
  • Ctrl+C during schedule loop is caught explicitly, prints a clean shutdown message, and closes the run-store — matching paper-live's own established graceful-shutdown pattern.
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
10

Known limitations, stated honestly

  • No real NSE/BSE holiday calendar integration. Holidays are a plain, user-supplied date list (empty by default) — the same "recognized, never silently faked" posture market_data.universe.py already applies to unimplemented NIFTY index modes, and the same documented limitation live/dhan/market_session.py already states for session detection.
  • The scheduler is still a foreground process. schedule loop must be kept running by something (a terminal, a Windows service wrapper, nohup/systemd on Linux) — this phase does not install itself as an OS-level service, which was not asked for and would be a separate, larger scope.
  • Restart recovery is deterministically tested, not battle-tested against a real kill -9. See §07's evidence table.
  • Multi-day continuous operation remains unproven, same honest gap Phase 27 already stated — this phase supplies the mechanism that makes it possible, not the elapsed-time evidence itself.
