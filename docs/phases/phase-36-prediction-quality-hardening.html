Scope & audit findings

Per the roadmap's own framing for this phase ("Audit and improve"), the work here was reviewing the EXISTING Phase 23 pipeline against every named area -- prediction identity, duplicate prevention, outcome resolution, stop/target ordering, corporate actions, market gaps, unresolved-prediction aging -- rather than building new features by default. Several areas were already sound on inspection (same-bar stop/target ambiguity, expiration handling, append-only history) and are documented as such, not re-fixed. Three real, demonstrated gaps were found and closed.

03

Finding 1: no structural price-ordering guard

`PredictionRecord` could be constructed with stop_price >= entry_price

The invariant (stop below entry below target, for a long) held only because risk.sizing.build_signal_for_buy's own upstream guards happened to always produce a sane Signal -- nothing on PredictionRecord itself enforced it. Fixed with a model_validator requiring stop_price < entry_price < target_price, the same "type system forecloses it" posture Decision's own evidence-requirement validator already uses.

04

Finding 2: no duplicate prevention

Running `predict`/`shadow-run` twice against an unchanged bar silently double-recorded

Each call to make_decision() generates a fresh, random decision_id regardless of whether the underlying evidence changed, so nothing stopped an accidental re-run (a re-executed script, a double-clicked scheduler tick) from creating a second, redundant prediction for the exact same entry bar -- silently inflating prediction counts and skewing win-rate statistics. Fixed with PredictionStore.has_prediction_for_entry(symbol, entry_time), keyed on bar-granularity entry_time (not decision_id, which is always unique) -- catches "the same day's data was recorded twice" while still allowing a genuinely NEW prediction the next day.

05

Finding 3: no corporate-action guard

An unadjusted stock split between entry and evaluation would look like a catastrophic stop-hit

This project fetches Yahoo data with auto_adjust=False and integrates no split/dividend adjustment source. A 2:1 split between a prediction's entry and its later evaluation would make the raw post-split price look like an ~50% single-bar collapse relative to the pre-split entry_price -- evaluate_prediction would have silently resolved that as a genuine STOP_HIT, an economically meaningless and simply wrong outcome. Fixed with a bar-to-bar (not entry-to-bar) implausible-move check: if any bar's range moves >=50% from the PREVIOUS bar's close, evaluation stops and returns INSUFFICIENT_DATA with an explicit "likely stock split" detail, rather than fabricating a false outcome. Checking against the previous close (not the original entry price) specifically avoids flagging a genuine, gradual multi-bar decline as an anomaly -- only a sudden jump is.

Safety

  • All three fixes are refusals/guards, not new capabilities -- no new order-placement or broker-mutation path anywhere in this phase.
  • The append-only audit history principle is unchanged: a duplicate is REFUSED before insertion, never deleted or rewritten after the fact; the corporate-action guard still writes a normal, permanent PredictionEvaluation row (just with an honest INSUFFICIENT_DATA outcome instead of a fabricated one).
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
09

Known limitations, stated honestly

  • No actual stock-split has been observed and correctly caught in production. The guard is deterministically tested against synthetic data; a real split occurring during this project's operation, and being correctly flagged rather than silently misresolved, remains NOT VERIFIED until one actually happens.
  • The 50% anomaly threshold is a stated, conservative default, not tuned against real split-frequency data. A stock that genuinely moves >=50% in one real trading day (rare, but possible for micro-caps) would also be flagged as "insufficient data" rather than resolved -- an intentional false-positive tradeoff in favor of never fabricating an outcome from bad data.
  • Duplicate prevention is keyed on entry_time, not a broader "same opportunity" concept. A decision whose evidence changes meaningfully within the same day (e.g. two different scans) but happens to price against the same daily bar would still be treated as a duplicate -- a deliberate, conservative choice given this project's daily-bar-granularity default, not an oversight.
