Phase 39 — Long-Run Operations & Recovery

One Bad Tick Should Never Kill a Week-Long Loop

An audit-first phase: before adding anything, this pass re-read Phase 28's scheduler (restart recovery, overlap prevention, duplicate-scheduling protection via BEGIN IMMEDIATE) and Phase 30's resilience module (circuit breaker, retry-with-backoff, provider timeouts) and found them already solid -- no changes needed there. What WAS genuinely missing: an exception outside run_tick's own per-slot error handling could kill the entire schedule loop process, there was no persistent log for a multi-day unattended run, and no quick way to check database health after one. All three are fixed here, narrowly.

02

Scope

In scope: (1) isolating an unexpected tick-level exception inside schedule loop so it cannot kill the whole process; (2) an optional, size-bounded rotating log file (--log-file) for persistent unattended logging; (3) a read-only schedule status --check-integrity DB health check; (4) a deterministic multi-day simulation proving the scheduler's existing correctness holds across many ticks, not just one.

Explicitly out of scope, and why: active database pruning/retention -- this project's own established convention everywhere else (predictions, experiments, decisions) is an append-only audit trail that is never overwritten or deleted; adding a retention policy here would contradict that invariant, and at this project's realistic scale (a handful of scheduler slots firing a few times a day) SQLite with its existing indices handles years of history without difficulty. A process-level (multi-OS-process) duplicate-scheduling test -- Phase 28's existing thread-based concurrency test already exercises the exact mechanism (SQLite's own OS-level file locking via BEGIN IMMEDIATE) that makes cross-process safety hold; SQLite's locking model does not distinguish threads from processes, so a slower, flakier subprocess-based test would prove nothing new.

What was built

schedule loop's while-loop, before: while ...: result = _run_tick_from_args(...) # an exception HERE killed the whole process ... schedule loop's while-loop, after: while ...: try: result = _run_tick_from_args(...) except KeyboardInterrupt: raise # Ctrl+C still stops the loop except Exception as exc: tick_failures += 1 logger.exception(...); print(...) # logged and visible, then continues ... python main.py schedule loop --log-file scheduler.log ... -> attaches a RotatingFileHandler (10MB x 5 backups) to the SAME root logger setup_logging() already configures -- stdout output is unchanged either way python main.py schedule status --check-integrity -> PRAGMA integrity_check + file size, read-only, no data touched

The tick-level exception this closes is real, not hypothetical: run_tick already wraps _execute_slot (an ordinary operational failure -- bad symbol, provider outage -- becomes a FAILED RunRecord), but nothing wrapped reclaim_stale_locks, active_lock, due_slot, or try_start_run themselves -- a transient SQLite lock-contention error from those (plausible if an operator runs both schedule loop and a cron-triggered schedule tick against the same database, a scenario Phase 28's own docstring already names) would have propagated all the way out and ended the unattended process.

Safety

  • The loop-level except-and-continue re-raises KeyboardInterrupt explicitly before the broad except Exception -- verified by a dedicated test that Ctrl+C still stops the loop even immediately after a prior tick failure.
  • integrity_check and db_size_bytes are read-only (a PRAGMA query and a file stat) -- no code path here writes to, prunes, or otherwise mutates any database.
  • add_rotating_file_handler only ever adds a handler, never removes or replaces the existing stdout handler setup_logging() installed -- console behavior is byte-for-byte unchanged whether or not --log-file is passed.
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
07

Known limitations, stated honestly

  • Real multi-day, real-wall-clock unattended operation has not happened yet. The roadmap's own acceptance criterion ("test days of repeated runs") is partially about real elapsed time this phase cannot fabricate -- the 10-simulated-day / 60-tick test proves the scheduling LOGIC is correct across many ticks, which is the right way to test logic without waiting, but it is not a substitute for actually running schedule loop --log-file ... unattended for real days and later checking schedule status --check-integrity and the log file. That remains an outstanding, honestly-named, time-dependent validation step.
  • A loop-level tick failure (caught by the new except-and-continue) is not recorded as a structured RunRecord -- because it happens before try_start_run is ever reached, there is no run_id to attach it to. It is visible via the console/log-file line and a running tick_failures count printed at loop shutdown, but not queryable later via schedule status the way a FAILED slot execution is. A dedicated "loop-level incidents" table was considered and rejected as unjustified complexity for a failure mode that, so far, has only been reproduced synthetically in tests.
  • No consecutive-failure circuit breaker. If every tick fails for a persistent reason (e.g. the run-db file becomes genuinely corrupted), the loop will keep retrying forever at the configured poll interval rather than giving up after N failures -- a deliberate choice (an arbitrary "give up after N" threshold would be an unjustified, untested policy), but worth an operator knowing: persistent failures are visible in the log, not self-terminating.
