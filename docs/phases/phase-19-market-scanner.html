02

Roadmap reconciliation, stated up front

PROJECT_GOAL_AND_ROADMAP.md's own phase numbering names its Phase 18 "Market Intelligence Foundation" (market data abstraction + universe + market state + data quality) and its Phase 19 "Market Scanner & Candidate Discovery." What was actually built and merged as this repository's "Phase 18" (market_data/) covers the roadmap's Phase 18 core — abstraction, universe, data quality — deliberately scoped down per your own explicit instruction (watchlist-only, no SectorSnapshot/MarketRegime, no state persistence layer). This phase is therefore the roadmap's Phase 19 in substance, continuing the repository's own sequential numbering. SectorSnapshot/MarketRegime remain deferred; this phase's own sector-strength factor (see §06) is a scanner-local approximation, not the roadmap's future regime/sector-snapshot machinery, and is documented as such rather than presented as satisfying that later requirement early.

03

Scope

In scope: a scanner that takes a MarketUniverse and produces a ranked, explainable ScanReport — liquidity/price/volume screening gates (configurable, no-op by default absent evidence for a real threshold), then trend/momentum/breakout/relative-strength/sector-strength scoring; SQLite persistence of every scan; a scan CLI subcommand.

Explicitly out of scope: no buy/sell/BUY-WATCH-AVOID output (roadmap Phase 21), no entry/target/stop/quantity, no AI/LLM involvement anywhere in the scoring path, no research/news evidence (roadmap Phase 20), no capital or risk sizing, no change to market/indicators.py, market_data/, or any existing strategy/risk/paper module.

04

What was built

market_intelligence/ models.py CandidateScore, ExcludedCandidate, ScanReport -- Pydantic, matches paper/*.py's persisted-model convention config.py ScannerConfig -- every gate/weight named, defaulted to a no-op or equal weight, version_id() for audit scanner.py run_scan() -- pure function: MarketUniverse + MarketDataProvider -> ScanReport store.py ScanHistoryStore -- SQLite, same convention as paper/store.py (data_json + model_validate_json)

main.py scan wires it up: --symbols or --watchlist-file, a CachedMarketDataProvider(YahooFinanceProvider()) exactly like backtest/paper run already use, prints the ranked list with each candidate's explanation, and persists every run to data/scanner.db.

05

Screen -> score pipeline (matches the roadmap's own diagram)

Market Universe -> Liquidity Filter (avg daily value, configurable floor) -> Price Filter (min/max, configurable) -> Volume Filter (volume_ratio floor, configurable) -> Volatility Filter (ATR% of price bounds, configurable) -> Trend Detection +-- -> Breakout Detection | scored, weighted, summed into -> Relative Strength | composite_score -- every term -> Sector Strength +-- also kept as its own field -> Candidate Ranking (sorted desc, ties broken by symbol)

A symbol failing any gate is excluded, never scored — recorded in ScanReport.excluded with a specific reason string (data fetch failure, insufficient history, liquidity/price/volume/volatility floor), so "why was this stock not a candidate" is answerable from the report alone. One symbol's fetch failure or bad data never aborts the scan for the rest of the universe.

Every gate defaults to a no-op (0.0 / None) rather than a fabricated cutoff — no liquidity or volatility study has been run against this project's actual data yet, so a specific numeric floor is left for whoever runs that study, matching the evidence-only-after-evidence discipline research/volume_signal.py already established in Phase 11.

06

What was reused, not rewritten

  • market.indicators.compute_indicator_series — every technical primitive (SMA20/50, RSI14, ATR14, volume ratio) is read from its existing causal output; no indicator math is recomputed.
  • market.data_provider.MarketDataProvider Protocol — run_scan takes the provider as a required argument (no internal default), so a caller decides live/cached/fake and a test can never accidentally reach the network.
  • backtesting.cache.CachedMarketDataProvider — wired at the CLI layer exactly as run_backtest_command/run_paper_command already do, not duplicated inside market_intelligence/.
  • market_data.universe.MarketUniverse (Phase 18) — the scanner's only universe representation; not a second one.
  • paper/store.py's persistence convention — ScanHistoryStore mirrors it exactly: stdlib sqlite3, one file, explicit transaction, data_json round-tripping through the real model's own validator.
  • risk.config.RiskConfig.version_id()'s pattern — ScannerConfig.version_id() is the identical sha256-of-model_dump_json construction, so a ScanReport records exactly which threshold values produced it.

research/alpha_features.py's relative-strength-vs-market computation was deliberately not imported, even though it computes something similar — research/ is a naming collision already flagged and explicitly deferred to its own rename task (Phase 18's report, §06); deepening a dependency on it here during this phase would work against that eventual rename. The scanner's relative-strength math is written fresh, independently, using the same trailing-return methodology.

07

Sector strength: an honest limitation, not a fabrication

No sector-index data source is integrated anywhere in this project. Rather than fabricate one or hardcode a sector list, sector strength is optional and computed only from the scanned universe's own composition: if the caller supplies a symbol -> sector mapping, each sector's mean trailing return is compared against the scanned universe's own mean — "is this symbol's sector outperforming the rest of what was just scanned," not "is this sector outperforming the market." Symbols with no sector tag, or a scan run with no sector_map at all, get sector_strength_score = None, reported in the explanation as "not available," never silently defaulted to 0 disguised as a real observation.

Tests

09

Safety

  • Zero imports of paper/, risk/, or any broker adapter anywhere in market_intelligence/ — a CandidateScore cannot reach an order-placing code path because none exists in its dependency graph.
  • No credentials used or referenced — this phase only fetches historical OHLCV through the existing, already-audited Yahoo provider path.
  • No hidden network calls in the unit test suite (25 of 28 new tests use an in-memory fake provider; the 3 CLI tests use real on-disk cached data, matching the established repository convention).
10

Known limitations, stated honestly

  • Every gate threshold defaults to a no-op — running scan with defaults against a real watchlist will surface illiquid/penny-priced symbols alongside real candidates until a caller supplies real, evidence-based thresholds. This is intentional (see §05), not an oversight, but is worth knowing before reading a default-config scan's output as curated.
  • Sector strength requires the caller to supply a sector map by hand; no sector taxonomy is looked up automatically from any source.
  • The scanner fetches full historical OHLCV per symbol (needed for rolling indicators) rather than using Phase 18's lighter-weight MarketSnapshot facade — a deliberate choice (the facade only exposes the latest bar, not history), not an oversight; the two packages serve different questions and neither duplicates the other's data model.
  • Composite-score factor weights are equal by default and explicitly un-tuned — no historical evaluation has been run to justify any other weighting yet.
