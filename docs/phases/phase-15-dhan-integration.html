Dhan API verification (2026-09-01/02, current docs)

Re-verified directly against docs.dhanhq.co and dhanhq.co/docs/v2 (both JS-rendered SPAs, read via live browser rendering, not a static fetch) rather than trusting Phase 14's research notes. One real correction found:

Phase 14's notes described only the full 3-step OAuth "API key & secret" flow. The current docs make clear that's the flow for partner platforms serving other users. For a single individual trader (this project's actual shape), Dhan offers a much simpler path: generate a 24-hour access token directly from web.dhan.co, or via a TOTP-based POST /app/generateAccessToken endpoint, plus a /RenewToken API to refresh an active token without regenerating. live/dhan/config.py is built around this simpler individual-trader flow.

Exact APIs used

  • wss://api-feed.dhan.co?version=2&token=...&clientId=...&authType=2 — live tick feed, Ticker mode only.
  • GET https://api.dhan.co/v2/fundlimit, /positions, /holdings — read-only.
  • https://images.dhan.co/api-data/api-scrip-master.csv — public, unauthenticated instrument master.

No order-placement endpoint (/orders, /super/orders, /forever) is referenced anywhere in live/dhan/ — enforced by a structural test, not just by not having written the code.

04

Authentication approach

DHAN_CLIENT_ID / DHAN_ACCESS_TOKEN read from the process environment only, at the moment a real call is about to be made — never at import time, never hardcoded. .env.example documents the variable names with empty values; the real .env pattern was already excluded by Phase 13's .gitignore. DhanCredentials.__repr__ masks both fields so a stray print() or debugger session can't leak them.

Market-data architecture

06

Symbol mapping

live/dhan/instruments.py never treats a Yahoo symbol as a broker identifier. "RELIANCE.NS" is parsed for its exchange suffix, then looked up in the real instrument master by (exchange, segment, trading_symbol) — disambiguating equity from futures/options sharing the same underlying name. Confirmed against the real downloaded file: NSE,E,2885,EQUITY,...,RELIANCE,... — Security ID 2885.

07

Tick/candle handling

Dhan streams ticks, not candles (confirmed — no candle-shaped feed mode exists in the documented Request Codes). CandleBuilder's semantics are stated explicitly, not left implicit: bucket boundaries floored to the interval from the Unix epoch; open/high/low/close from the tick sequence; volume summed only from what each tick actually carries (Ticker packets carry none — 0.0 is used honestly rather than fabricated); a bar is only emitted the instant a tick from the next bucket arrives — no wall-clock timer forces one out early, and a silent bucket with no ticks produces no bar at all (never a manufactured flat candle).

08

Freshness

Reused live.freshness.FreshnessPolicy completely unchanged. Tested through the real pipeline: a live Dhan-sourced bar within threshold reaches BAR_PROCESSED normally; a bar timestamped far outside threshold reaches STALE_SIGNAL_SUPPRESSED; duplicate/out-of-order protection (also unchanged, living in PaperTradingEngine) applies identically to Dhan-sourced bars. No second freshness system was created.

09

Connection management & disconnect behavior

connect → authenticate (via the URL's own query params) → subscribe → receive → on disconnect, bounded exponential backoff (default base 1s, cap 30s) up to max_reconnect_attempts (default 5) → a terminal FAILED state, never an unbounded retry loop. Once FAILED, next_bar() raises FeedDisconnectedError on every subsequent call — proven with a test that forces every reconnect attempt to fail and confirms the connect function is called exactly max_reconnect_attempts times, not more.

No price is ever manufactured or reused stale during a disconnect: CandleBuilder simply stops receiving ticks; the pipeline's own freshness gate and the FEED_DISCONNECTED result together prevent new signals until a fresh, valid bar actually arrives.

10

Read-only account integration & reconciliation

Real design deviation from Phase 14's proposal, and the reason: Phase 13's BrokerAdapter protocol returns paper-shaped types (risk.account.Account, paper.models.Position) because MockBrokerAdapter only ever delegated to PaperTradingEngine. A real Dhan funds/positions response doesn't map onto those types without either dropping real Dhan fields or fabricating paper-only ones (daily_start_equity, consecutive_losses) that have no broker equivalent — doing that would violate this phase's own instruction to never mix broker and paper account state. So DhanAccountReader does not implement BrokerAdapter; it has its own honestly-typed read methods (DhanFundLimit, DhanPosition, DhanHolding), rendered under their own "DHAN ACCOUNT" heading wherever they appear, never merged with "PAPER ACCOUNT."

Reconciliation: the existing reconcile_against_broker() (Phase 13) was not extended to call DhanAccountReader this phase — it still expects a BrokerAdapter-shaped object, which DhanAccountReader deliberately isn't. Real Dhan-vs-paper reconciliation is explicitly listed under §18 as unbuilt, not silently skipped.

16

Bugs discovered & fixed

NO_NEW_BAR: a real interface gap, not hypothetical production bug — fixed

MarketDataSource.next_bar()'s original contract used bare None to mean "the feed has permanently ended" — correct for a finite scripted replay, wrong for a real WebSocket that's simply between candles. Wiring DhanMarketDataSource into the existing pipeline surfaced this immediately: a quiet moment would have been reported as FEED_EXHAUSTED, stopping the CLI as if the feed had died. Fixed with a new NO_NEW_BAR sentinel (live/contracts.py) and a corresponding NO_NEW_DATA pipeline result — MockMarketDataSource's existing behavior is completely unchanged (it never returns the sentinel).

Own test used near-1970 epoch ticks against a 2026 pipeline clock test bug — not production

Early integration tests used epoch=60/121 as tick timestamps with a 1,000,000× freshness multiplier — not nearly generous enough for a 56-year gap (versus the ~5-year AAPL-data gap that multiplier was tuned for in Phase 13). Fixed by using realistic epoch timestamps near the fixture clock.

Own "duplicate bar" test misunderstood CandleBuilder's forward-only state test bug — not production

A single CandleBuilder can never "resend" an already-closed bucket — its internal state only moves forward. Rewritten to simulate the realistic case this actually models: a reconnect, where a fresh CandleBuilder (new source instance, same engine) redelivers a bar for an already-processed bucket.

.gitignore's .env.* pattern also excluded .env.example fixed before push

.env.example (documents variable names, no real values, meant to be tracked) was being silently swallowed by the same pattern meant to exclude real secret files. Fixed with an explicit !.env.example negation, caught before the commit that would have hidden it.

Two hardcoded MCP tool-count assertions fixed

Same recurring pattern as Phase 13: test_mcp_paper.py and test_mcp_server.py each hardcode the total tool count as a security-relevant sanity check. Both correctly caught the 3 new tools and were updated (20 → 23) with the new count's derivation documented in a comment, matching the file's own established convention.
