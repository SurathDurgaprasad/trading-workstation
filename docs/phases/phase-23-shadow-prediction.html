Phase 23 — Shadow Prediction & Continuous Evaluation

The System Keeps Score, Whether You Trade or Not

A new predictions/ package records what a BUY decision implied (entry/stop/target), then checks real subsequent market data against it — whether or not the user ever traded it. Every prediction is immutable; what later happens to it is a separate, appended row, never a rewrite. This is the roadmap's own "core requirement": the system keeps learning even at zero trades.

02

Scope

In scope: recording a BUY decision's implied entry/stop/target as an immutable PredictionRecord; monitoring real subsequent market data to resolve it (TARGET_HIT/STOP_HIT/EXPIRED/ACTIVE/INSUFFICIENT_DATA), each check appended as a new PredictionEvaluation; a basic aggregate summary (win rate, average return, profit factor) — the roadmap's own target long-term architecture lists "evaluation" and "performance metrics" as predictions/'s own subcomponents, distinct from a separate future learning/ package.

Explicitly out of scope: cross-strategy comparison, confidence calibration, and anything claiming actual "learning" in a stronger sense — the roadmap's own section 8 ("What Learning Means") places that at Level 2/3, which is Phase 24's job ("Performance Learning System"), not this one. No order, real or paper, anywhere in this phase.

03

What was built

predictions/ errors.py PredictionUnavailableError -- mirrors risk.sizing.SizingUnavailableError's role models.py PredictionOutcomeState, PredictionRecord, PredictionEvaluation, PredictionSummary tracker.py create_prediction(), evaluate_prediction(), summarize_predictions() store.py PredictionStore -- TWO linked, append-only tables (predictions, prediction_evaluations)

main.py predict --symbol X reads the latest BUY Decision, builds its Signal via the unchanged risk.sizing.build_signal_for_buy (Phase 22), records a PredictionRecord, and persists it. main.py evaluate loads every prediction still needing a check (never evaluated, or last seen ACTIVE), resolves each against real market data via the same CachedMarketDataProvider pattern backtest/paper/scan already use, appends a new PredictionEvaluation row for each, and prints a summarize_predictions() roll-up.

predictions/store.py is the first genuinely two-table store among this session's new packages: market_intelligence/research/decision_engine's stores have all been single append-only tables so far. Here, a PredictionRecord and its (possibly many, over time) PredictionEvaluation rows are linked by prediction_id — the closest existing precedent is paper/store.py's own signals/risk_decisions/orders/fills/positions/trades split. No update_prediction or update_evaluation method exists anywhere in the class, asserted directly by a test.

04

Outcome states: five produced, five recognized

Roadmap section 7.3 suggests ten outcome states. This phase's evaluation logic can only honestly produce five of them from real subsequent market data:

StateStatusWhy
ACTIVEPRODUCEDNeither target nor stop hit yet, horizon not reached, and/or not enough bars fetched yet to know
TARGET_HIT / STOP_HITPRODUCEDResolved by walking forward through real subsequent bars
EXPIREDPRODUCEDHorizon reached with neither hit
INSUFFICIENT_DATAPRODUCEDThe market data fetch itself failed
MISSED_ENTRYRECOGNIZED, NOT PRODUCEDAssumes a limit-style order that might never fill; every prediction here enters immediately at the sizing bar's own close
INVALIDATED / PARTIAL_SUCCESS / CANCELLED / PENDINGRECOGNIZED, NOT PRODUCEDEach needs a judgment call this project has no evidence-based rule for yet

All ten remain real enum members (a typo or an unhandled future state fails clearly) — the same "recognized future extension, never silently faked" posture market_data.universe.py already applies to unimplemented NIFTY-index modes.

05

What was reused, not rewritten

  • backtesting.execution.check_exit / OpenPosition — called directly for the same-bar-ambiguity stop/target check ("if a single bar's range could have hit both, the stop wins"). Not reimplemented; a dedicated test (test_evaluate_prediction_same_bar_ambiguity_reuses_check_exits_stop_wins_rule) constructs exactly that ambiguous bar and asserts the shared function's own answer comes through unchanged.
  • risk.sizing.build_signal_for_buy (Phase 22) — the sole source of a prediction's entry/stop/target; predictions/ never re-derives price-level math.
  • market.data_provider.MarketDataProvider Protocol / backtesting.cache.CachedMarketDataProvider — the existing historical-data path, wired at the CLI layer exactly as backtest/paper run/scan already do; no new data source.
  • decision_engine.store.DecisionStore (Phase 21) — predict reads the latest decision from it unchanged, the same composition pattern decide and size already use for their own upstream stores.
  • risk.sizing.SizingUnavailableError's posture — PredictionUnavailableError mirrors it exactly (a non-BUY label or a symbol mismatch fails closed with a clear error, never a fabricated prediction).
06

Self-audit: adversarial edge cases checked

  • Division by zero in win rate / average return / profit factor. All three are explicitly None-guarded for zero resolved predictions and (for profit factor) zero losing predictions — covered by three dedicated tests, including the fully-empty-input case.
  • A hit on the exact horizon bar. The loop checks check_exit BEFORE the horizon-reached check on every iteration, so a target/stop hit on the last allowed bar reports TARGET_HIT/STOP_HIT, never EXPIRED — verified directly (test_evaluate_prediction_hit_on_the_exact_horizon_bar_takes_priority_over_expiration), not just assumed from reading the code.
  • No bars exist yet after entry_time. Explicitly handled before the walk-forward loop even starts: ACTIVE, bars_observed=0, zero excursions — not a crash, not a false EXPIRED.
  • Double-counting or skipping a boundary bar. Filtering uses strict > on entry_time (never >=), so the entry bar itself is excluded exactly once and every later bar is visited exactly once — both entry_time and the fetched frame's index are naive-normalized the same way market/indicators.py already does, so no timezone-mismatch could silently duplicate or drop a bar.
  • A re-evaluated, since-resolved prediction being double-counted in the summary. summarize_predictions deduplicates to each prediction's LATEST evaluation by evaluated_at before tallying anything — verified with a dedicated test using an older ACTIVE row and a newer TARGET_HIT row for the same prediction.

Tests

44 new tests (pytest-collected count, verified directly via pytest --collect-only per file rather than assumed, after this session was burned twice already by trusting an assumed number): 20 in test_predictions_tracker.py (creation validation, every outcome state including the same-bar-ambiguity and exact-horizon-boundary cases, excursion tracking, and the full summarize_predictions math), 7 in test_predictions_models.py (enum completeness for both the produced and recognized-but-unproduced state sets, immutability, ID uniqueness), 10 in test_predictions_store.py (the two-table linked design, list_predictions_needing_evaluation's real behavior against this venv's actual bundled sqlite3, no update methods, reconnect persistence), and 7 CLI tests (arg parsing for both subcommands, missing-decision handling, one end-to-end predict run through real stores, and a zero-predictions evaluate run). No real network or Ollama call anywhere in the unit suite, and no data/market/ cache files are written by any test (verified via git status immediately after the run). Full regression: 747 passed, 0 failed.

08

Safety

  • Zero imports of paper/ or any broker adapter anywhere in predictions/.
  • Both CLI commands print explicitly that no trade, real or paper, is placed. A prediction is a hypothetical record tracked for its own sake — converting a BUY decision into an actual paper trade remains the entirely separate, unchanged paper/paper-live path.
  • No credentials used or referenced — this phase only reads historical OHLCV through the already-audited Yahoo provider path.
09

Known limitations, stated honestly

  • BUY only, same as Phase 22. WATCH/AVOID/NO_ACTION correctly have no price levels to track; EXIT is a "close what you hold" instruction, not a fresh prediction to monitor.
  • No automatic scheduling. evaluate must be run by the user (or an external scheduler) periodically; this phase does not add a background loop or daemon.
  • list_predictions_needing_evaluation is O(n) in Python, not a single SQL window-function query. A window-function approach was considered but the simpler, directly-verified Python-side approach (list predictions, check each one's latest evaluation) was chosen deliberately for this phase's scale (a local, single-user tool) rather than trusting an unverified SQL feature.
  • The aggregate summary is Level-1 only (win rate, average return, profit factor) — no market-condition-aware comparison, no confidence calibration. That is explicitly Phase 24's job.
