02

Reconciliation: one app, one more route

dashboard/app.py (Phase 13) and tests/test_dashboard.py were read in full before writing anything. The existing app is a single-file Starlette process, plain HTML string rendering (no template engine, no JS framework), reading through live/workstation.py — a thin, read-only facade module with monkeypatchable module-level DB path constants. That exact shape is reused here rather than reinvented: dashboard/intelligence.py is the same kind of facade for the Phase 18-25 pipeline's stores, and the new page is one more Route(...) entry on the SAME app = Starlette(...) instance already wired to python main.py dashboard — not a second app, a second port, or a second CLI command.

03

Scope

In scope: a new /intelligence page showing the latest persisted scan (ranked candidates, each with its latest decision label if one exists) and a prediction-performance summary (strategy comparison, signal quality) — everything the roadmap's own Phase 26 question list asks for except entry/stop/target/position-size/confidence per opportunity (see §09).

Explicitly out of scope: any change to the existing paper-live workstation view or its approve/reject/kill-switch routes (untouched, re-verified by the full existing test suite); any market-data fetch, LLM call, or store write triggered by a page load; a new UI framework or a second dashboard process.

04

What was built

dashboard/intelligence.py SCANNER_DB_PATH / RESEARCH_DB_PATH / DECISIONS_DB_PATH / PREDICTIONS_DB_PATH -- same PROJECT_ROOT/data/<name>.db + TRADING_*_DB_PATH env-var override convention as live/workstation.py's LIVE_SIM_DB_PATH/LIVE_STATE_DB_PATH get_latest_scan() -> ScanReport | None get_latest_decision(sym) -> Decision | None get_latest_research(sym) -> ResearchReport | None get_learning_snapshot() -> dict | None (provider-free analysis only -- see §09) dashboard/app.py intelligence_page(request) -- one new route handler, same inline-HTML style as index() app = Starlette(routes=[..., Route("/intelligence", intelligence_page, methods=["GET"])])

The existing / page gained one link ("Market intelligence & prediction performance →"); /intelligence links back. Every candidate/decision/config-version string rendered into the page goes through html.escape(), the same discipline index() already applies to symbols and free-text fields.

05

What was reused, not rewritten

  • live/workstation.py's exact facade pattern — module-level, monkeypatchable DB path constants with an env-var override, read-only functions, no business logic in the route handler.
  • market_intelligence.store.ScanHistoryStore, decision_engine.store.DecisionStore, research.store.ResearchStore, predictions.store.PredictionStore (Phases 19-23) — read unchanged.
  • learning.analysis.compare_by_config_version / compute_confidence_calibration / compute_signal_quality (Phase 24) — called directly; compute_regime_performance/build_learning_report's regime part is deliberately NOT called here (see §09).
  • dashboard/app.py's own _page() wrapper, CSS classes (tag, kv, muted, banner), and html.escape() discipline — the new page looks and behaves like part of the same app because it reuses the same rendering primitives, not a copy of them.
06

Self-audit: adversarial edge cases checked

  • A candidate with no decision on record. Explicitly tested: renders "no decision recorded" rather than crashing on a None lookup.
  • Zero market-data/LLM calls on page load. Verified directly with a fresh grep across dashboard/intelligence.py and dashboard/app.py for fetch_ohlcv/invoke_structured/check_ollama_availability — none found.
  • HTML escaping of evidence-sourced strings. Tested directly with a symbol containing <script> markup, confirming the raw tag never appears in the response and the escaped form does.
  • No accidental coupling to the paper-live engine. An early draft of the test suite called client.get("/") from a test file that did not isolate live/workstation.py's own module-level DB path constants the way test_dashboard.py's dedicated fixture does -- caught before it could write to the real repository's data/live_sim_trading.db as a side effect of an unrelated test. Removed in favor of adding one assertion to test_dashboard.py's own, already-isolated existing test instead. git status on data/ confirmed clean after the full new suite ran.
07

Tests

5 new tests in test_dashboard_intelligence.py (empty state with no databases yet, a populated scan with a matching decision, a candidate with no decision, a populated learning snapshot, and the HTML-escaping case), plus one new assertion added to test_dashboard.py's existing, already-isolated test_index_renders_empty_workstation proving the new /intelligence link is present. All 8 pre-existing test_dashboard.py tests re-run and confirmed unaffected. No real network, Ollama call, or market-data fetch anywhere in the unit suite -- verified both by the grep in §06 and by the tests requiring no such fakes at all. Full regression: 787 passed, 0 failed.

08

Safety

  • dashboard/intelligence.py imports nothing from paper/ or any broker adapter.
  • There is no action route on /intelligence at all — it is GET-only, no forms, no POST targets. The page's own banner states plainly that no order of any kind can be placed from it.
  • The existing paper-live workstation's approve/reject/kill-switch routes are byte-for-byte unchanged.
09

Known limitations, stated honestly

  • No entry/stop/target/position-size/confidence per opportunity. The roadmap's own Phase 26 question list asks for these; showing them live for every ranked candidate would require running size (a real market-data fetch) for each one on every page load, which this phase deliberately avoids (see §03). The existing size/predict CLI commands remain the way to get that detail for one symbol at a time.
  • No market-regime performance on this page. learning.analysis.compute_regime_performance needs a live/cached market-data provider; get_learning_snapshot() deliberately omits it rather than trigger a fetch on every GET. python main.py learn remains the way to see it.
  • Single-universe snapshot. The page shows the SINGLE latest scan report, not a history of scans over time.
  • No research evidence shown yet. get_latest_research() exists in dashboard/intelligence.py but is not yet rendered on the page — a natural next increment, deferred rather than rushed into this phase's already-broad scope.
