Phase 33 — Market Regime & Market Breadth Intelligence

Explainable Aggregates, Not Opaque Scores

A new market_intelligence/regime.py turns an already-computed ScanReport into market breadth (advance/decline, free -- pure aggregation) and a benchmark's own trend + volatility regime (one fresh fetch, reusing Phase 24's classify_regime_at and Phase 19's own ATR14 indicator), plus optional sector strength. New regime CLI command; scan now prints breadth automatically. Found and fixed two real bugs along the way, one of them a deep, previously-undiscovered defect in this project's core timestamp normalization.

Scope

In scope: market breadth (advancing/declining/flat, advance/decline ratio -- a pure aggregation over an existing ScanReport, zero extra cost); benchmark trend regime (reusing learning.regime.classify_regime_at verbatim) and volatility regime (current ATR14%-of-price vs. its own trailing average, an explicit named-threshold classification); optional sector strength (grouping candidates by an externally-supplied sector map, the same shape research.sector.build_sector_map already produces). A new regime CLI command; scan prints breadth automatically.

Explicitly out of scope: any AI-driven regime classification (the roadmap's own rule for this phase: "No opaque AI output should silently control labels" -- every number here is a plain aggregation or an existing indicator, nothing else); a universe-wide volatility aggregate (would need scanner-level ATR persistence, a schema change not attempted this phase -- benchmark-only volatility was chosen instead, the same "one index's own volatility" pattern VIX-style measures use).

Bug 1: a dead tzinfo-stripping branch, project-wide

`market.data_provider._to_timestamp` never actually stripped tzinfo from real DataFrame index values

Found not by inspection but by a real crash: a genuine scan --symbols AAPL,MSFT,GOOGL (default ^NSEI benchmark) raised TypeError: Cannot compare dtypes datetime64[us, UTC+05:30] and datetime64[us] inside the scanner's relative-strength reindex. Root cause: pd.Timestamp IS a `datetime` subclass, so `_to_timestamp`'s `isinstance(value, datetime): return value` branch matched EVERY real `.iterrows()` index value and returned it completely as-is -- the tzinfo-stripping code three lines below was dead for the one call site that matters (`OHLCV.from_dataframe`), only ever running for a raw non-Timestamp input like a string. `^NSEI`'s Yahoo data happens to carry an Asia/Kolkata-aware index; most US-symbol data apparently doesn't -- so the bug silently violated this project's own "Yahoo/mock bars are naive by convention" invariant (relied on in live/freshness.py, market_data/quality.py, and learning/regime.py) for any symbol whose Yahoo response happened to include tzinfo, and simply never surfaced as a visible crash until two differently-aware series were compared directly. Fixed by resolving the Timestamp-vs-raw-value branch first, THEN unconditionally checking/stripping tzinfo.

A second, narrower related bug: learning.regime.classify_regime_at itself raised the same class of InvalidComparison when called with a genuinely UTC-aware as_of (exactly what this phase's own benchmark classification needs to pass) against naive bars -- Phase 24's original call site always passed an already-naive as_of, so this never surfaced until Phase 33's new caller exercised it. Fixed by normalizing `as_of`'s awareness to match the bar index's own (never inventing a timezone for the bar data itself), mirroring the exact naive/aware duality this project already documents everywhere else.

05

Bug 2: a benchmark override silently ignored

`regime --benchmark X` computed X's regime... except it didn't

Caught by a failing CLI test, not by inspection: run_regime_command correctly resolved a `--benchmark` override into a local variable but never actually passed it to build_market_regime_report, which always read scan_report.benchmark_symbol directly -- an override was silently discarded. Fixed by adding an explicit benchmark_symbol parameter to the library function, using a module-level sentinel (USE_SCAN_REPORTS_OWN_BENCHMARK) to distinguish "caller didn't specify, inherit the scan's own" from an explicit None ("disable regardless of what the scan used") -- a real ambiguity a plain `None` default couldn't express, since `None` already means "no benchmark" to `compute_benchmark_context`.

08

Safety

  • Read-only throughout -- regime writes nothing, places no order, changes no configuration.
  • Every classification is a named, explainable formula (threshold multipliers stated in the code and docs) -- no AI call anywhere in this module.
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
09

Known limitations, stated honestly

  • Volatility regime is benchmark-only, not universe-wide. A genuine per-scan volatility breadth would need ATR persisted on `CandidateScore` -- a schema change not attempted this phase.
  • Volatility thresholds (1.5x/0.67x) are stated defaults, not tuned against historical performance -- the same "equal weight / no fabricated threshold until proven otherwise" posture `ScannerConfig` already documents for its own gates.
  • The _to_timestamp fix has project-wide reach beyond this phase's own new code -- every existing test suite was re-run in full to check for regressions (953 passed, 0 failed), but this is worth an operator's attention as a genuinely deep fix, not a narrow one.
