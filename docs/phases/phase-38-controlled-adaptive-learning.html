Phase 38 — Controlled Adaptive Learning

A Recommendation, Never a Mutation

The roadmap for this phase is explicit: "DO NOT allow uncontrolled autonomous strategy mutation... No automatic production promotion without evidence thresholds. All changes must be auditable." A new learning/adaptation.py adds exactly one function, compare_and_recommend — a pure, deterministic verdict over two already-registered Phase 37 experiments, gated by two fixed, stated thresholds. It never touches a config file, never chooses what to compare, and never promotes anything. It only explains, in full, why or why not.

02

Scope

In scope: a pure function compare_and_recommend(baseline, candidate) over two Phase 37 ExperimentComparison objects, returning a PromotionRecommendation with a verdict (INSUFFICIENT_EVIDENCE / NO_IMPROVEMENT / RECOMMEND_PROMOTION) and a fully auditable reasoning: list[str] trail; a new python main.py experiment recommend --baseline-id ... --candidate-id ... CLI command wiring it to the two experiments a human names.

Explicitly out of scope: generating parameter candidates or new experiments automatically (a human still runs experiment start for both sides); running a backtest or shadow evaluation (Phase 27's shadow-run and Phase 37's tracking already exist for that); applying a recommendation to any config file (there is no code path anywhere in this project, before or after this phase, that writes to decision_engine/config.py, market_intelligence/config.py, or risk/config.py programmatically).

03

What was built

python main.py experiment recommend --baseline-id A --candidate-id B -> compare_experiments([A, B], items, store) # Phase 37's own function, unmodified -> compare_and_recommend(baseline=comparison_A, candidate=comparison_B) compare_and_recommend, in order: 1. same config_version on both sides? -> INSUFFICIENT_EVIDENCE (not a meaningful comparison) 2. resolved < MIN_SAMPLE_SIZE (30) either side? -> INSUFFICIENT_EVIDENCE 3. win_rate is None either side? -> INSUFFICIENT_EVIDENCE 4. candidate.win_rate - baseline.win_rate >= MIN_IMPROVEMENT_MARGIN (10pp)? yes -> RECOMMEND_PROMOTION no -> NO_IMPROVEMENT every branch appends its own numbers to `reasoning` -- nothing is silent

Both thresholds are named module constants, not buried literals: MIN_SAMPLE_SIZE_FOR_PROMOTION = 30 (a stated, conservative rule-of-thumb -- the reasoning text itself calls even 30 samples "small" for a trading strategy, not a proof) and MIN_IMPROVEMENT_MARGIN = 0.10 (10 percentage points, deliberately wide to absorb small-sample noise). Neither was tuned against any historical result in this project.

Safety

  • Every recommendation prints "ADVISORY ONLY, NO CONFIGURATION IS CHANGED" and a closing reminder that promotion requires a manual config edit plus a fresh experiment start -- the audit trail this phase's roadmap text requires is Phase 37's own append-only experiment registry, unchanged.

07

Known limitations, stated honestly

  • Win rate is the only promotion signal. Average return and profit factor are printed as reasoning context but do not gate the verdict -- a candidate could clear the win-rate margin while having a worse average return; the CLI output surfaces both numbers so a human reviewing the recommendation can catch that, but the verdict itself does not.
  • No statistical significance test. MIN_SAMPLE_SIZE_FOR_PROMOTION and MIN_IMPROVEMENT_MARGIN are stated, conservative rules of thumb, not a computed p-value or confidence interval -- Phase 41 (Profitability Evidence Framework) is where confidence intervals are planned, not here.
  • Overlapping experiment windows are still not warned about (a gap Phase 37's own report already named) -- a recommendation computed over two experiments with overlapping time windows and the same config_version would silently double-count, though the identical-config_version guard in this phase catches the exact-same-config case specifically.
