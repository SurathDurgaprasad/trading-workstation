02

Scope

In scope: timeout, retry with exponential backoff + jitter, a circuit breaker, an optional minimum-interval rate limiter, in-process provider metrics, and opt-in integration at every multi-symbol/multi-prediction loop this project has (scan, shadow-run, evaluate, learn, and the Phase 28 scheduler that drives all of them).

Explicitly out of scope: making resilience the new DEFAULT everywhere (see §04's reasoning for why opt-in was the deliberate, conservative choice); the single-fetch commands (decide's risk-context lookup, size/predict's uncached get_market_context call) remain unwrapped -- a real, named limitation, not an oversight (§08).

03

What was built

market_data.resilience.ResilientMarketDataProvider(inner) .fetch_ohlcv(symbol, ...) 1. circuit_breaker.allow_request()? NO -> raise immediately, zero network attempt 2. respect_rate_limit() -> sleep if calls are faster than min_interval_seconds 3. attempt (up to max_attempts): run inner.fetch_ohlcv on a DAEMON thread, wait up to timeout_seconds success -> record metrics, circuit_breaker.record_success(), return failure -> record metrics, circuit_breaker.record_failure() sleep(exponential backoff + jitter), retry 4. all attempts exhausted -> raise MarketDataError (unchanged exception type -- every existing caller's `except MarketDataError` already handles it)

Every dependency (sleep, clock) is injectable, so the full unit suite never sleeps for real except one deliberate test proving the timeout mechanism itself under genuine concurrency.

04

The bug caught before it shipped

`ThreadPoolExecutor` would have made a genuinely hung network call block the WHOLE process at exit

The first design considered concurrent.futures.ThreadPoolExecutor for the timeout (the obvious, idiomatic choice). Working through it before writing any code: ThreadPoolExecutor's worker threads are non-daemon, and both its own with ...: ... context-manager exit (shutdown(wait=True)) and Python's interpreter-shutdown atexit hook BLOCK until every submitted call finishes -- so a genuinely hung network call would make the fetch itself "time out" correctly, but then make the entire python main.py scan ... process hang at exit anyway, waiting for the abandoned thread. That would have defeated the entire point of adding a timeout. Caught by reasoning through the design, not by a failing test -- the implementation instead uses a plain threading.Thread(daemon=True) with a queue.Queue, which the process can exit immediately regardless of, and this is proven directly by test_timeout_returns_promptly_without_waiting_for_a_hung_call: a fake provider that sleeps 2s against a 0.1s timeout, asserting the call returns in well under 1s.

05

Where it's wired in, and why opt-in

--resilient was added to scan, shadow-run, evaluate, learn, and both schedule tick/schedule loop (threaded through the scheduler's constructed CLI args). It is deliberately NOT the new default: wrapping every existing provider construction unconditionally would silently add background-thread timeout enforcement to dozens of already-passing tests that fixture-patch get_market_data_provider/CachedMarketDataProvider directly, changing their execution characteristics (thread spawning, timeout semantics) without those tests asking for it -- exactly the kind of unrequested, invisible behavior change the project's own engineering principles warn against. Opt-in delivers the real capability (tested, real-service-verified) without that risk; an operator running schedule loop unattended -- the scenario this matters most for -- passes --resilient once.

08

Safety

  • No new network destination, no new dependency -- wraps the EXISTING MarketDataProvider protocol exactly, and every raised error is still a plain MarketDataError (or the new ProviderCircuitOpenError subclass), so every existing per-symbol exception handler needs zero changes.
  • Daemon threads cannot outlive or block the main process -- verified directly (§04).
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
09

Known limitations, stated honestly

  • Opt-in, not default. A user who never passes --resilient gets zero protection from this phase -- see §05 for why that trade-off was made deliberately.
  • Single-fetch commands remain unwrapped. decide's risk-context lookup and size/predict's get_market_context call don't offer --resilient -- less exposed to the "many sequential requests" failure mode this phase targets, but a real, named gap for a future pass.
  • A real, sustained outage has not been observed in production. The mechanism is real and tested; graceful degradation against an actual live outage is NOT VERIFIED (§06) -- the same honest posture every other "infrastructure exists, real-world proof requires real-world conditions" limitation in this project already has.
