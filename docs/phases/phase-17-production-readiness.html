03

Findings

1. Ollama-dependent test misclassified as a hard dependency FIXED — MEDIUM

Finding: test_explain_signal_tool_returns_only_the_explanation_schema failed whenever no local Ollama daemon was running, even though its own stated intent (and its sibling test in test_signal_explainer.py, which already passes offline) is to verify the MCP tool's output schema using a fully mocked LLM.
Root cause: explain_signal_tool correctly calls check_ollama_availability() as an unconditional pre-flight guard before the mocked LLM is ever reached — this is correct production behavior (documented in the tool's own docstring), but the test never mocked that guard, so it could never reach its actual assertions without a real daemon. The guard's own failure paths are independently, already covered offline by test_failure_handling.py.
Decision: Category B (per Phase 17's own classification options) — the application handles Ollama absence correctly; the test setup was wrong.
Fix: the one test now also mocks llm.provider.check_ollama_availability. No production code changed.
Result: the full suite now passes standalone, with zero external-service dependency, matching the goal that pytest should be trustworthy and self-contained by default.

2. Market data source never closed on any exit path FIXED — HIGH

Finding: run_paper_live_command never called source.close() — not on normal completion, not on Ctrl+C, not on any path. For --source dhan this meant the real WebSocket connection was never deliberately closed by the CLI itself; a Ctrl+C additionally propagated as a raw, uncaught KeyboardInterrupt traceback. A related, smaller issue: a failed reconciliation triggered sys.exit(1) before store.close()/state_store.close() ran.
Reproduction: grep -n "source.close" main.py returned no matches anywhere in the file, confirmed by direct code reading.
Fix: the main loop is now wrapped in try/except KeyboardInterrupt/finally; source.close() runs unconditionally on every exit path, Ctrl+C is caught and reported cleanly instead of crashing, and store.close()/state_store.close() now run before any exit call, including the reconciliation-failure path.
Tests: two new regression tests prove source.close() is called on both normal completion and a simulated KeyboardInterrupt, using a tracked MockMarketDataSource.close.

04

Startup & configuration

Empirically tested, not just read: missing Dhan credentials, an unknown strategy name, and Ollama being unreachable each produce a single clean line on stderr and a controlled non-zero exit — never a raw stacktrace, never a partial start, never a leaked value. main()'s _CONTROLLED_ERRORS tuple is the single, deliberate mechanism behind this and was verified to cover exactly the exceptions these commands can actually raise.

One documentation gap found and fixed: the two Ollama models this project needs by default (qwen2.5-coder:7b, nomic-embed-text) were never named anywhere a new operator would find them. README now states them explicitly, alongside an explicit statement that every other command works with Ollama entirely absent.

06

Lifecycle & shutdown

The DhanMarketDataSource close/reconnect race, orphan-connection prevention, and bounded-retry state machine were already exhaustively audited and hardened in Phase 16 (generation-tagged locking, stability-gated retry reset) and were not re-litigated here beyond confirming the tests still pass. What Phase 17 added: the CLI layer above it now actually calls close(), on every exit path, which Phase 16's own work could not have caught since it never audited main.py itself. The dashboard's shutdown is delegated to uvicorn.run(), which has its own well-established SIGINT/SIGTERM handling; not re-implemented here.

07

Observability

An operator already has real, working tools without reading source: python main.py paper status (equity, cash, drawdown, open positions, trade/signal counts, reconciliation result), the dashboard's MARKET FEED section (reads the feed_status table written on every real bar — source, status, connection state, last-received timestamp), the paper-live CLI's own per-bar printout (bar timestamp, freshness, open position P&L), and structured logging added in Phase 16 for every Dhan connection-state transition. This was reviewed and found sufficient for this project's actual scale; no new dashboard, health-check endpoint, or metrics stack was added, per this phase's explicit "prefer minimal" instruction and the absence of any demonstrated gap large enough to justify one.

10

Persistence & duplicate-execution risk

Read directly, not assumed: PaperStore wraps every multi-statement write in an explicit BEGIN/COMMIT/ROLLBACK transaction (no partial writes on failure), and journal_entries.signal_id carries a database-level UNIQUE constraint. PaperTradingEngine additionally checks find_journal_entry_by_signal_id before ever attempting to process a signal, explicitly returning DUPLICATE_SKIPPED rather than relying on the constraint to fail. Since Signal.stable_id() is deterministic, a bar redelivered after a crash/restart (or a Dhan reconnect replaying a bucket) cannot produce a second paper execution for the same signal — verified both by direct code reading and by the existing test_duplicate_dhan_bar_is_skipped_by_the_existing_engine test.
