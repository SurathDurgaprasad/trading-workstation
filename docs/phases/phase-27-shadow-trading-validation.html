Infrastructure for Validation, Not Validation Itself

A new shadow-run command chains every existing pipeline stage — scan, research, decide, predict, evaluate, learn — into one pass over a watchlist, pure orchestration over already-tested functions. What this phase deliberately does NOT claim: the roadmap's own acceptance criterion is to run this "for sufficient time before considering higher-risk functionality," and real elapsed time cannot be produced inside a coding session. This phase ships the infrastructure that validation needs; it does not fabricate the validation itself.

02

Reconciliation: what Phase 27 actually asks for

The roadmap's own text: "Run the complete system without real orders" through Live Market → Research → Analysis → Recommendation → Shadow Prediction → Outcome → Evaluation, then "Run for sufficient time before considering higher-risk functionality." Every stage of that pipeline already existed as a separate, already-merged CLI command (scan/research/decide/size/predict/evaluate/learn, Phases 19-24) before this phase started. What was genuinely missing was orchestration: a way to run all of them in one pass over a watchlist instead of five-plus manual invocations per symbol.

What this phase does not attempt: fabricating "sufficient time" evidence. Running shadow-run once, or even several times in one sitting, is not what the roadmap is asking for — it is asking whether the system's real recommendations hold up over real trading days. That requires the user's own ongoing operation (directly, or via a scheduler running shadow-run periodically) and their own judgment about when enough time has passed. This report classifies that criterion NOT VERIFIED, not "complete," per the project's own evidence-classification discipline — see §06.

03

Scope

In scope: a new shadow-run CLI command orchestrating scan → research → decide → predict for a watchlist, then evaluate → learn over all outstanding predictions (skippable via --skip-evaluate); one real, bounded, honestly-classified end-to-end validation run.

Explicitly out of scope: any claim of "sufficient time" validation (see §02); any scheduling/daemon infrastructure to run shadow-run automatically (the user's own cron/Task Scheduler, pointed at this new command, is sufficient and is not this project's concern to build); any new risk/decision/prediction logic — every stage's own math is completely unchanged.

04

What was built

main.py: run_shadow_run_command() [1/4] run_scan(...) -> ScanReport, persisted [2/4] for each candidate: build_research_report(...) -> ResearchReport, persisted make_decision(...) -> Decision, persisted if label == BUY: build_signal_for_buy(...) -> Signal create_prediction(...) -> PredictionRecord, persisted (one symbol's failure is caught, logged, and printed -- the rest of the universe still runs) [3/4] evaluate_prediction(...) for every prediction needing one [4/4] summarize_predictions(...) -- win rate / avg return printed

Every arrow above is a call into an existing, already-tested function — run_shadow_run_command itself contains no new business logic, only sequencing, per-symbol error isolation, and printing. --with-ai (default off) opts every symbol into the optional AI research summary and decision narrative; left off, a bulk run needs no Ollama at all. --skip-evaluate stops after recording predictions, for a caller who only wants the "generate today's recommendations" half.

05

What was reused, not rewritten

  • market_intelligence.scanner.run_scan, research.summarizer.build_research_report, decision_engine.engine.make_decision, risk.sizing.build_signal_for_buy, predictions.tracker.create_prediction/evaluate_prediction/summarize_predictions — the exact same functions their own standalone CLI commands already call, in the exact same order those commands compose them in (decide reading scan's output, predict reading decide's, etc.).
  • The per-symbol optional --paper-db open-position lookup — identical to decide's own existing use of it, not a new risk-context source.
  • market_intelligence.scanner's own "one symbol's fetch failure never aborts the scan" posture — shadow-run applies the identical discipline one level up, around the research/decide/predict block for each candidate.
06

Evidence: one real run, classified honestly

Before merge, shadow-run was run once against real, live Yahoo Finance data (no Dhan, no credentials needed) for a single real symbol:

$ python main.py shadow-run --symbols AAPL --benchmark "" --skip-evaluate [1/4] Scan complete: 1 candidates, 0 excluded. [2/4] AAPL composite=-0.13 decision=AVOID Run summary: 1 candidate(s) scanned; decisions: AVOID=1; predictions recorded: 0.

This is real, not fabricated: a genuine composite score computed from AAPL's real recent price history, a genuine AVOID label because that score was not positive. The temporary databases this run wrote to were deleted afterward (confirmed via git status both before and after — nothing under data/ was ever tracked).

07

Self-audit: adversarial edge cases checked

  • One candidate's decide/predict stage failing. Tested directly: a symbol whose market-context fetch raises mid-run is caught, logged, and printed as FAILED -- the rest of the watchlist still completes and gets real decisions/predictions.
  • A declining universe producing zero BUY decisions. Tested directly with a synthetic downtrend -- confirms no prediction is fabricated when nothing qualifies, and the run still completes cleanly (an early draft of this same test used a naive negative price step that would have driven OHLCVBar.close non-positive over 100 bars, violating that model's own gt=0 constraint -- caught and fixed by starting the synthetic series from a high enough base before the test was ever run, not after a failure).
  • Resource cleanup across the per-symbol loop. Verified by reading the code fresh: the four stores are opened once and closed exactly once each, after the loop (or in the early-return --skip-evaluate branch) -- a per-symbol exception never leaves a store open twice or skips closing it.
  • Structural safety. tests/test_dhan_no_real_orders.py and tests/test_broker.py re-run both before and after this phase's changes, per the project's own standing rule for any phase touching decisions/risk -- all 12 passed both times.

10

Known limitations, stated honestly

  • "Sufficient time" validation has not happened. This is the phase's own central, honest limitation -- see §02 and §06. shadow-run is the tool; running it repeatedly over real time, and judging when enough has accumulated, is the user's.
  • No built-in scheduler. Deliberately not built -- the user's own cron/Task Scheduler pointed at python main.py shadow-run ... is sufficient infrastructure, and building a second one inside this project would be premature.
  • One real run only covered the AVOID path. The real-data run in §06 happened not to produce a BUY, so the predict leg's real-service evidence remains at the LOCAL/DETERMINISTIC TEST VERIFIED level (via the fixtures in §08), not REAL SERVICE VERIFIED -- an honest gap, not glossed over.
