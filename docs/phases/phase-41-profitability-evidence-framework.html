Phase 41 — Profitability Evidence Framework

A Verdict, Never a Claim

The roadmap's own rule for this phase: "the system must NOT claim profitability." A bare win rate cannot honor that -- a 60% win rate from 8 trades is noise, and an asymmetric-risk/reward strategy can be genuinely profitable below 50%. learning/profitability.py adds the one thing that was missing: a confidence interval for the mean per-trade return, and a verdict computed from whether that interval excludes zero -- INSUFFICIENT_DATA, STATISTICALLY_MEANINGLESS, POSITIVE_PERFORMANCE, or NEGATIVE_PERFORMANCE, always with the exact numbers that produced it.

02

Scope

In scope: sample size, win rate with a 95% Wilson score interval, average win/average loss, expectancy, profit factor (reusing learning.analysis's existing formula), a sequential trade-return max drawdown, return volatility, a 95% confidence interval for the mean per-trade return, sector performance grouping, and the four-way verdict itself -- all read-only, pure functions over already-evaluated predictions.

Explicitly out of scope, and why: a real Sharpe ratio -- this project tracks no risk-free rate and trades are not evenly time-spaced, so "return volatility" is reported as a plain per-trade standard deviation and explicitly labeled NOT a time-normalized Sharpe ratio rather than fabricating one. A t-distribution exact interval instead of the normal approximation -- the normal approximation is standard and adequate at the same n=30 floor this project already uses elsewhere (learning.adaptation), and using two different statistical conventions in two places would be worse than one clearly-stated approximation everywhere.

03

What was built

compute_profitability_report(items): returns = resolved predictions' actual_return, sorted by entry_time if len(returns) < 30: -> INSUFFICIENT_DATA mean, 95% CI = normal-approximation confidence interval of the mean if CI straddles 0: -> STATISTICALLY_MEANINGLESS elif CI entirely > 0: -> POSITIVE_PERFORMANCE else (CI entirely < 0): -> NEGATIVE_PERFORMANCE also computed: win_rate + Wilson CI, avg_win, avg_loss, expectancy (= the exact mean, see the bug below), profit_factor, max_drawdown (sequential compounding equity curve over the SAME sorted returns), return_volatility (sample stdev) compute_sector_performance(items): group by decision.research_evidence.sector.sector, or "Unknown" same win_rate/average_return formula as every other grouping in learning/analysis.py

Wired into learn's CLI output (new "Sector performance" and "Profitability evidence" sections) and the /intelligence dashboard page (a new card, colored green/red/neutral by verdict) -- both read from the SAME LearningReport.profitability/sector_performance fields, computed once in build_learning_report / dashboard.intelligence.get_learning_snapshot.

04

Bug found in self-audit

The first implementation computed expectancy the textbook way: win_rate * average_win + (1 - win_rate) * average_loss. Re-reading it adversarially before shipping: a resolved prediction with actual_return of EXACTLY 0.0 (a real, if rare, possibility -- e.g. an EXPIRED prediction that closed flat) counts in neither average_win (requires r > 0) nor average_loss (requires r < 0), yet win_rate's complement, 1 - win_rate, still gets multiplied by average_loss as if every non-winning trade were a loss at that rate. The two formulas silently diverge whenever a breakeven trade exists. Fixed by using the exact mean of all resolved returns directly (mathematically always correct, and simpler) -- a dedicated regression test constructs 10 wins, 10 losses, and 1 exact-zero breakeven and asserts the two formulas produce DIFFERENT numbers, proving the fix matters rather than just restating the same value differently.

Safety

  • Every function in learning/profitability.py is read-only over an already-passed-in list -- no store access, no network call, no config file touched.
  • The verdict enum has no "PROVEN_PROFITABLE" or similarly overstated value -- the strongest positive value is POSITIVE_PERFORMANCE, and every code path that reaches it also appends a reasoning line stating the interval is "directional evidence, not proof."
  • tests/test_dhan_no_real_orders.py / tests/test_broker.py: 12/12 passed before and after this phase's changes.
08

Known limitations, stated honestly

  • The normal approximation for the mean-return confidence interval is a large-sample approximation, applied starting exactly at its own conventional floor (n=30) -- for a sample just above that floor, a t-distribution interval would be modestly wider (more conservative). Using the normal approximation everywhere keeps this project's stated statistical convention singular rather than introducing a second one.
  • max_drawdown is a sequential trade-return equity curve, not a real day-by-day account curve. It applies each resolved trade's return in entry-time order to a single compounding unit of capital, which does not model overlapping positions, position sizing, or capital actually at risk at any given moment -- a deliberate, stated approximation.
  • No sample size has been reached yet in this project's own real usage to produce anything but INSUFFICIENT_DATA in practice -- this is expected and correct at this stage, not a defect; the framework exists so that a genuine verdict becomes possible once enough real, resolved predictions accumulate (the same real-world elapsed-time dependency named in every earlier phase's report).
