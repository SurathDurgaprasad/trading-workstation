## PHASE 2 — Live market data integrity

**Real finding: this machine's system clock is ~130 seconds behind true time.** Verified two independent ways that agree closely:
- Every one of the 10 bars in capture #1 showed `source_timestamp` (Dhan's own last-trade-time) running ~129s *ahead* of `received_at` (local wall-clock at tick receipt) — consistent across all 10 bars (129.0–129.9s), not random noise.
- A dedicated, independent cross-check against Dhan's own **HTTP response `Date` header** (a completely separate code path from the WebSocket LTT decode logic) measured **-130.3s** skew (local clock behind Dhan's server clock).

These two independently-measured numbers agree to within 1 second, which is strong evidence this is genuine **local machine clock drift**, not a Dhan-side or decode-side bug. This is the *same class* of risk as the historical, already-fixed "IST-labeled-as-UTC" bug (a systematically-wrong "now" silently understates data staleness in `FreshnessPolicy` checks) but two orders of magnitude smaller in this instance (~130s vs. ~5.5 hours) and caused by the environment, not the code. **Recommendation: sync this machine's system clock via NTP before further live sessions**, and be aware that any freshness/staleness safety check on this specific machine is currently biased toward reporting data *fresher* than it truly is by ~130s.

Other integrity checks, all PASS:
- **IST vs UTC handling**: every displayed timestamp converted correctly (cross-verified `bucket_timestamp`, `source_timestamp`, and `received_at` against manual IST conversion in the capture output — e.g. bucket `2026-09-07T03:54:00+00:00` = `09:24:00 IST`, correct).
- **Stale tick detection**: `FreshnessResult(is_fresh=True, ...)` computed correctly on every real bar; the freshness threshold (180s) comfortably exceeds the ~70-130s clock-drift-driven "age" seen, so no false staleness was triggered this session — but see the recommendation above for a machine with worse drift.
- **Duplicate/out-of-order/missing tick handling**: `rejected_tick_counts_by_symbol()` was `0` across every category (`non_positive_price`, `negative_volume`, `implausible_deviation`, `late_out_of_order`, `implausible_timestamp`) for all 5 symbol-sessions observed — the real feed was clean; none of this session's earlier-fixed defenses needed to fire.
- **Reconnect behavior**: no disconnect occurred naturally during either capture (a genuine network-level interruption was not tested this session — see Phase 9).
- **Symbol/instrument mapping**: both symbols resolved to their real, correct Dhan security IDs.
- **Price/volume sanity**: RELIANCE.NS traded in the ₹1317–1320 range, TCS.NS in ₹2279–2285, INFY.NS in ₹1100–1103 across the session — plausible, consistent real prices.
