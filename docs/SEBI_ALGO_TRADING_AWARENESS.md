# SEBI / Indian Market Constraint Awareness

INDIAN MARKET TRADING BRAIN mission, Phase 2. **This is engineering
awareness documentation, not legal or regulatory certification.**
Nothing here should be read as a compliance sign-off, and nothing here
was written by verifying against SEBI's own primary-source circulars
directly (no access to SEBI's own document repository from this
session) — every regulatory claim below is sourced from a live web
search performed 2026-09-08, with links given, and should be
re-verified against SEBI's own published circulars before this project
(or anyone using it) makes any decision that depends on the details
being exactly right. If this project is ever extended toward real
capital, consult SEBI's own materials and the broker's own compliance
team directly — this document's job is to make sure that step isn't
skipped out of ignorance, not to replace it.

## 1. Why this matters for this specific project, precisely

This project is **structurally incapable of placing a real order** —
verified repeatedly across many sessions in this project's own history
(no order-placement code path exists anywhere in the codebase; every
"order" is a row in `paper.store.PaperStore`, never a call to a
broker's order-entry endpoint). Because of that, most of SEBI's algo-
trading compliance machinery (order tagging, strategy registration,
Order-to-Trade Ratio monitoring) does not currently apply to this
system **as it exists today** — those frameworks govern the placing of
real orders, and this system places none. This document exists so that
fact stays true deliberately, not by accident, and so the moment
anyone considers extending this system toward live execution, they
know exactly what regulatory machinery would then apply.

## 2. The current regulatory framework (as found, with sources)

SEBI issued a circular in February 2025 on safer participation of
retail investors in algorithmic trading, with the framework becoming
**fully enforceable from April 1, 2026** — a phased rollout, not an
immediate cutover (broker registration applications were due
October 31, 2025; progressive strategy registration November 30, 2025;
mock trading session participation by January 3, 2026).

Key mechanisms, as reported:

- **Algo-ID tagging**: every order generated by an algorithm must
  carry a unique, exchange-assigned Algo-ID, applying to orders from
  brokers, registered algo providers, AND individual API-based retail
  traders alike, from April 1, 2026.
- **API order-rate threshold**: orders placed via API are classified
  as "algo orders" (requiring an Algo-ID) once the order-per-second
  rate crosses a threshold the exchanges themselves define — meaning
  even a retail trader using a broker's API for MANUAL-speed order
  entry may not be captured, but anything programmatic/automated
  almost certainly is.
- **Order-to-Trade Ratio (OTR) framework**: a separate SEBI circular
  (dated February 4, 2026, effective April 6, 2026) revises OTR
  monitoring — the ratio of orders placed to orders actually executed,
  used to flag excessive/spammy order placement.
- **Registration requirement**: retail algorithmic strategies are
  expected to be registered and routed through exchange-approved
  systems via the broker; an unregistered algorithm (including a
  homegrown API-based one) is still treated as algo trading and must
  comply once it crosses into real order placement.

Sources: [SEBI Algo & API Trading Rules 2026 — Bigul](https://bigul.co/blog/market-update/sebis-new-api-algo-trading-rules-from-april-2026-key-changes-explained), [SEBI Algo Trading Regulations 2026 — Liquide](https://blog.liquide.life/sebi-algo-trading-regulations-2026/), [SEBI's New Algo Trading Rules 2026 — UTrade Algos](https://www.utradealgos.com/blog/decoding-sebis-new-algo-trading-rules-for-retail-investors-all-you-need-to-know), [SEBI Algo Trading Rules 2025–2026 — AlgoBulls](https://algobulls.com/blog/industry-insights-and-updates/sebi-new-algotrading-regulations-for-retail-investors-2026).

## 3. What this means for THIS project specifically

| SEBI mechanism | Applies to this project today? | Why |
|---|---|---|
| Algo-ID order tagging | **No** | No order is ever placed with a real broker; there is nothing to tag. |
| OTR monitoring | **No** | Same reason — OTR measures real orders vs. real trades. |
| Strategy registration | **No** | Registration governs live algorithmic order flow; a paper-only research system generates no such flow. |
| Broker API terms (rate limits, static IP) | **Partially, already** | The system DOES make real, read-only Dhan REST/WebSocket calls (account reads, live quotes) — these are subject to Dhan's own API terms regardless of SEBI's algo-order rules, covered in §4. |

**If this project is ever extended to place real orders**, every row
in the left column flips to "Yes," and the engineering work required
(Algo-ID plumbing, registration with the broker, OTR-aware order
throttling) would be substantial and must be done before, not after,
any real order is ever placed. This is named explicitly so it is a
deliberate future decision, not something discovered midway through
a live-execution feature.

## 4. Broker API constraints (Dhan) — real, sourced, relevant today

Dhan's own published REST API rate limits (verified via Dhan's own
support documentation, 2026-09-08):

| Endpoint category | Rate limit |
|---|---|
| Non-trading APIs | Up to 20 requests/second |
| Order APIs | Up to 10 requests/second |
| Data APIs | Up to 5 requests/second |
| Quote APIs | 1 request/second |

Source: [Dhan API rate limits](https://dhan.co/support/platforms/dhanhq-api/what-are-the-api-rate-limits-for-dhan/). Dhan also requires **static IP whitelisting** for API access (a
real, existing operational constraint — an unwhitelisted IP produces a
documented `DH-905 Invalid IP` error) and operates under its own SEBI
stock-broker registration (INZ000006031) — Dhan's registration covers
Dhan as a broker; it does not extend to or certify anything this
project builds on top of Dhan's API.

**A real, disclosed gap found while writing this document**:
`live/dhan/rest_client.py` has no client-side rate limiting of its
own — it relies entirely on Dhan's own server-side enforcement to
reject requests that exceed the table above. This project's OWN
`market_data/resilience.py` already has a working rate-limiter
(`ResilientMarketDataProvider._respect_rate_limit`, an injectable
minimum-interval throttle) — but it is currently used for the
Yahoo-facing `--resilient` path, and its own `min_interval_seconds`
defaults to `0.0` (no throttling) unless a caller explicitly sets it.
Given this project's real Dhan REST usage today is low-frequency
(occasional per-symbol calls during a scan, not high-frequency
polling), this has not caused an observed problem — but it is a real,
concrete hardening opportunity (wire the existing rate-limiter, with a
sub-1-req/s interval, around the Dhan REST client specifically) if
Dhan usage ever becomes more frequent. Not fixed in this pass — named,
not silently left for someone to discover the hard way.

## 5. Order logging / auditability — already real, already strong

This project's own existing architecture (built and proven across
many prior sessions, re-verified rather than re-described here)
already provides most of what a real audit trail needs, independent
of any SEBI requirement specifically: `decision_id` correlating
`Decision → Signal → JournalEntry → PredictionRecord`, `paper.store`'s
own append-only order/journal history, `strategy/promotion_store.py`'s
own audit trail for every promotion-gate evaluation, and
`scheduler/store.py`'s own run-history table. This is a genuine
strength: if this project ever needed to demonstrate "what did the
system decide, when, and why" to a regulator or an auditor, the
evidence chain already substantially exists — this document does not
propose rebuilding any of it.

## 6. What this document deliberately does NOT do

- It does not certify SEBI compliance for this project or for anyone
  using it.
- It does not invent specific SEBI circular numbers, clause text, or
  penalty provisions beyond what the cited sources state.
- It does not recommend or design a live-execution compliance
  architecture — that is out of scope until (and unless) this project
  is ever deliberately extended past paper trading, which remains an
  absolute, structural constraint today.

## 7. Recommendation

No code change is required today — this project's current, paper-only
structural guarantee already keeps it outside the scope of SEBI's
algo-order-tagging and OTR frameworks. The two concrete, low-risk,
optional hardening items surfaced here (a Dhan-specific client-side
rate limit; awareness of static-IP whitelisting as an operational
dependency) are worth doing at some point but are not urgent given
today's actual usage pattern, and are recorded here rather than
silently deferred.
