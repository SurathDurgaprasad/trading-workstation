# Final Failure Mode Analysis

Each scenario: FAILURE -> DETECTION -> SAFE RESPONSE -> RECOVERY -> USER
VISIBILITY. Evidence is labeled per scenario as one of:
**[VERIFIED-TEST]** (a real test exercises this, cited by path),
**[VERIFIED-CODE]** (confirmed by direct code reading this session, no
test forces the path), or **[ASSUMED]** (plausible from architecture,
not independently re-confirmed this session). See `FINAL_PRODUCT_AUDIT.md`
for the component map this analysis is built against.

---

### 1. Market data provider (yfinance) unreachable or returns an error

- **FAILURE**: network outage, yfinance API change, rate limiting.
- **DETECTION**: `YahooFinanceProvider` calls raise; callers catch exceptions at the fetch boundary.
- **SAFE RESPONSE**: `CachedMarketDataProvider` falls back to last-known-good cached data; scanner/decision paths that require fresh data refuse to produce a signal rather than using stale data silently mislabeled as fresh (staleness is checked, not ignored).
- **RECOVERY**: automatic on next successful fetch; no manual intervention needed.
- **USER VISIBILITY**: `cache-status` and `daily-report` surface staleness explicitly; dashboard shows data age.
- **Evidence**: **[VERIFIED-CODE]** (`backtesting/cache.py`, `market/data_provider.py` read this session) + pre-existing test coverage for cache fallback. Not re-run live against an actual yfinance outage this session.

### 2. Malformed or impossible OHLCV data (e.g., high < low, non-monotonic timestamps, duplicate bars)

- **FAILURE**: upstream data provider returns corrupt or out-of-order data.
- **DETECTION**: **fixed in the release-gate pass** -- `market_data/validation.py::validate_ohlcv` classifies a series HEALTHY/DEGRADED/INVALID (duplicate/non-chronological timestamps, symbol-identity mismatch, gaps, staleness); `market/data_provider.py::OHLCV.from_dataframe` also drops individual rows with an impossible OHLC relationship (high<low, close outside [low,high]), the same mechanism it already used for NaN rows. Live-tick-path candle-builder rejection counters (`docs/OBSERVABILITY.md`) remain a separate, pre-existing detection layer for that different path.
- **SAFE RESPONSE**: `market_intelligence/scanner.py`'s `_screen_symbol`/`_fetch_benchmark` exclude the symbol (`ExcludedCandidate`, never scored) on an INVALID report -- the exact "INVALID DATA -> NO PREDICTION/DECISION" rule this mission requires, verified by a dedicated failure-injection test.
- **RECOVERY**: automatic on the next fetch of clean data; no manual intervention needed.
- **USER VISIBILITY**: the exclusion reason (`"Data quality: ..."`) is visible in the scan report's `excluded` list, the same place a fetch failure already surfaces.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_market_intelligence_scanner.py::test_invalid_data_quality_is_excluded_not_scored`, `tests/test_market_data_validation.py` (11 tests), `tests/test_market_data.py::test_ohlcv_from_dataframe_filters_rows_with_impossible_ohlc_relationships`. **Residual, disclosed gap**: gap/missing-bar detection is a non-calendar-aware heuristic (DEGRADED, not INVALID -- a real market holiday can also trigger it); the offline `ml_research`/`quant_research` data paths are not yet gated by this validator, only the live scanner path.

### 3. LLM/RAG provider (Claude API) unreachable, rate-limited, or returns malformed output

- **FAILURE**: API outage, auth failure, malformed JSON response from the model.
- **DETECTION**: try/except around LLM calls in the critic/RAG layer.
- **SAFE RESPONSE**: the deterministic decision core does not depend on LLM output for BUY/SELL/HOLD -- LLM-derived context (e.g. critic narrative) is advisory/explanatory, not gating, confirmed by the earlier context-pipeline audit finding that market-context severity is capped at WARNING and WARNING does not block APPROVE. LLM failure should not prevent a decision from being reached.
- **RECOVERY**: automatic retry or graceful omission of the LLM-derived field on next cycle.
- **USER VISIBILITY**: partial -- an LLM failure is logged, not surfaced as a first-class dashboard status.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_failure_handling.py::test_rag_store_not_found_gives_actionable_error` (seen in this session's regression output) covers one RAG failure path. The broader "LLM DOWN -> SYSTEM CONTINUES" claim is **[VERIFIED-CODE]** by architecture (decision path does not call the LLM), not independently re-tested end-to-end this session with the API forcibly disabled.

### 4. Dhan broker unreachable / WebSocket disconnect

- **FAILURE**: network issue, Dhan-side outage.
- **DETECTION**: connection-state tracking in `live/dhan/market_data_source.py` (`DhanConnectionState`: DISCONNECTED/CONNECTING/CONNECTED/RECONNECTING/FAILED/CLOSED).
- **SAFE RESPONSE**: no order placement is attempted without a live, authenticated session; paper-execution continues unaffected since it never touches Dhan. Bounded exponential backoff with a terminal FAILED state after `max_reconnect_attempts` -- never an unbounded retry storm (a REAL past incident: this project's own Dhan client ID was rate-limited during live testing before this bound existed, per that module's own docstring).
- **RECOVERY**: automatic reconnect on a transient failure; FAILED is terminal until an explicit `subscribe()` call resets the retry budget. **Cycle 7 disclosed a gap** (no timeout on the CONNECTING state itself; the real transport runs `ping_interval=0`, no protocol-level keepalive -- a genuinely silent hang, TCP connects but the handshake/all subsequent traffic is silently dropped with no RST/FIN, would leave the feed stuck in CONNECTING indefinitely). **Cycle 8 revisited it via a structured 7-question re-audit and fixed it**: `connect_timeout_seconds` (default 30s) now routes a stalled CONNECTING attempt through the same `_report_connection_lost` funnel every other failure already uses -- no new state machine, inherits the existing generation-based dedup and bounded-reconnect-then-FAILED behavior. The re-audit's own conclusion: this was never a *safety* gap (`live/freshness.py`'s `FreshnessPolicy` is an independent downstream layer keyed on bar-timestamp-vs-wall-clock, so `STALE_DATA_NO_TRADE` engaged regardless) but WAS a genuine *recovery-failure* gap -- the silent hang specifically prevented this module's own reconnect machinery from ever self-healing, requiring a manual restart.
- **USER VISIBILITY**: connection status in live-state; `is_connected()` correctly reports `False` throughout a CONNECTING attempt (no false claim of health).
- **Evidence**: **[SIMULATED / VERIFIED]** -- `tests/test_dhan_market_data_source.py` (37 tests, several documented as fixes for real incidents against a live account, including 3 new cycle-8 watchdog tests: silent hang self-heals, a normal fast-opening connection is unaffected, `connect_timeout_seconds=None` preserves the exact pre-fix behavior) plus `tests/failure_injection/test_dhan_reconnect_simulation.py` (indexing disconnect/malformed-message/repeated-failure/reconnect-success/connecting-timeout scenarios into the executable failure matrix). Still **not** `[REAL PROVIDER / VERIFIED]` -- no Dhan credentials exist in this environment; that grade should never be claimed without one.

### 5. Live order execution attempted despite structural disablement

- **FAILURE**: a code path attempts to place a real order.
- **DETECTION**: `tests/test_dhan_no_real_orders.py` -- a dedicated "critical safety test" asserting the real-order code path is unreachable/disabled.
- **SAFE RESPONSE**: order placement is structurally blocked regardless of credentials, reachability, or model output ("LIVE ORDER -> BLOCKED BY DEFAULT" is enforced in code, not just policy).
- **RECOVERY**: N/A -- this is a permanent safety invariant, not a recoverable-from state.
- **USER VISIBILITY**: any attempted live order would raise/log loudly rather than silently no-op.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_dhan_no_real_orders.py` (ran clean in both this session's regression runs: 1976 and 1989 passed). This session's own `git diff --stat main` confirmed zero changes to `live/dhan/broker_adapter.py`, `live/broker.py`, `live/pipeline.py`, `decision_engine/rules.py`, `risk/engine.py` -- the live-execution-safety path is untouched by this session's work.

### 6. SQLite database corruption

- **FAILURE**: disk error, power loss mid-write, filesystem issue, or the file being overwritten by something else.
- **DETECTION**: two layers now. (1) **Autonomous hardening cycle 1 addition**: `core.sqlite_util.connect()` -- the ONE place every store opens its connection -- detects a corrupt/non-SQLite file automatically on every single connection attempt (not just when an operator remembers to run a check), raising a clear `DatabaseCorruptedError` naming the file instead of a raw `sqlite3.DatabaseError`. (2) `PRAGMA integrity_check`, exposed via `core.sqlite_util.integrity_check()` on all 12 stores, for a deeper on-demand scan an operator can run explicitly (e.g. after long unattended operation).
- **SAFE RESPONSE**: a corrupted file now fails LOUDLY and IMMEDIATELY at the first connection attempt (layer 1), rather than only being caught if/when an operator happens to run an explicit integrity check (layer 2). This closes what this document previously listed as a disclosed gap ("still not automatically invoked on every startup").
- **RECOVERY**: manual -- restore from a backup or accept data loss on the affected store; no automated repair (unchanged).
- **USER VISIBILITY**: the `DatabaseCorruptedError` message itself, at the moment any command tries to open the affected store -- documented in `TROUBLESHOOTING.md`. `integrity_check()` remains available for a proactive, deeper scan.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_core_sqlite_util.py::test_connect_against_a_corrupted_file_raises_a_clear_database_corrupted_error` and `test_connect_against_a_truncated_file_also_raises_the_clear_error` (autonomous hardening cycle 1); `PRAGMA integrity_check` coverage unchanged from the prior pass. **Residual, disclosed gap**: still no single CLI command surfacing all 12 stores' `integrity_check()` results together in one pass (`python main.py health --check-integrity`-style aggregation does not yet exist for every store, though `core.health.collect_system_health`'s database check does aggregate a `PRAGMA integrity_check` across every configured, existing store's path).

### 7. SQLite lock contention (scheduler + dashboard + CLI concurrent access)

- **FAILURE**: two processes touch the same DB file simultaneously.
- **DETECTION**: `sqlite3.OperationalError: database is locked` would previously surface at the default 5s stdlib timeout.
- **SAFE RESPONSE**: **fixed this session** -- WAL mode (concurrent readers do not block on an in-progress writer, verified by a real threading test) + 30s busy_timeout (vs. the previous 5s default) on all 12 stores, reducing but not eliminating lock-contention failures under sustained concurrent load.
- **RECOVERY**: automatic once the contending transaction completes, within the timeout window.
- **USER VISIBILITY**: an unresolved lock past 30s still raises, visibly, rather than hanging silently.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_core_sqlite_util.py` includes a genuine concurrent-reader-not-blocked-by-writer test using real threads, not a mock.

### 8. Disk full / write failure

- **FAILURE**: host disk fills up (market data cache, DB growth, logs).
- **DETECTION**: **autonomous hardening cycle 6 addition** -- `core.health._check_disk` now checks real free space (`shutil.disk_usage`) on the volume holding the data directory, in addition to its pre-existing real write-probe. Previously this would only ever surface as a raw `OSError`/`sqlite3.OperationalError` at the point of write, with zero advance warning.
- **SAFE RESPONSE**: DEGRADED below 500MB free (advance warning, does not block startup); FAILED below 50MB free (disk is a CRITICAL health component, so this correctly escalates overall status to FAILED and blocks the startup gate -- the same fail-closed posture a genuine write failure already gets). A `disk_usage`-specific lookup failure (distinct from an actual write failure, which the write-probe already proved works) degrades gracefully to HEALTHY-with-a-caveat rather than a false FAILED.
- **RECOVERY**: manual (operator frees space) -- unchanged; this closes the DETECTION gap, not the recovery mechanism, which was never automatable here.
- **USER VISIBILITY**: `python main.py health` and the dashboard `/health` route now report free space directly, before a write ever actually fails.
- **Evidence**: **[VERIFIED-TEST]** 4 new tests in `tests/test_core_health.py` (`test_disk_check_reports_healthy_with_ample_free_space`, `test_disk_check_reports_degraded_when_free_space_is_low`, `test_disk_check_reports_failed_when_free_space_is_critically_low`, `test_disk_check_survives_a_disk_usage_lookup_failure`).

### 9. Scheduler job raises an unexpected exception mid-slot

- **FAILURE**: any exception inside `_execute_slot` (e.g. a downstream command failure).
- **DETECTION**: pre-existing `except (Exception, SystemExit)` boundary around `_execute_slot` specifically (with its own documented historical incident: an uncaught `SystemExit` previously orphaned a lock).
- **SAFE RESPONSE**: the run is marked FAILED, the lock is released; the scheduler loop itself is not killed.
- **RECOVERY**: automatic on the next scheduled tick.
- **USER VISIBILITY**: `schedule status`/`list_runs` shows the FAILED run with an error message.
- **Evidence**: **[VERIFIED-TEST]** pre-existing coverage in `tests/test_scheduler_runner.py`, re-confirmed passing in both regression runs this session. Unmodified this session.

### 10. Scheduler tick-setup phase raises (lock reclaim, holiday check, slot selection)

- **FAILURE**: e.g. a database error while checking `active_lock()` before any slot has even started.
- **DETECTION**: previously **undetected as a distinct case** -- this code ran outside the `_execute_slot` exception boundary and could propagate uncaught out of `run_tick`, crashing a single `schedule tick` CLI invocation.
- **SAFE RESPONSE**: **fixed this session** -- the entire setup phase is now wrapped in its own outer exception boundary, returning a clean `TickResult(ran=False, reason=...)` instead of raising.
- **RECOVERY**: automatic on the next tick; no orphaned state since no slot was ever started.
- **USER VISIBILITY**: the failure reason is captured in the returned `TickResult` rather than an unhandled traceback.
- **Evidence**: **[VERIFIED-TEST]** new `tests/test_scheduler_runner.py::test_run_tick_does_not_crash_on_a_lock_acquisition_failure`, a real failure-injection test (monkeypatches `active_lock` to raise), passing in both regression runs.

### 11. Process crash / restart while a scheduler run is RUNNING

- **FAILURE**: the host process is killed (OOM, crash, manual kill, machine reboot) mid-run.
- **DETECTION**: on next startup, `reclaim_stale_locks(staleness_seconds=...)` finds RUNNING rows older than the staleness threshold.
- **SAFE RESPONSE**: such rows are marked RECLAIMED, releasing the lock so a new run can start; the on-disk RUNNING row (not an in-memory lock) is what makes this survive the crash.
- **RECOVERY**: automatic on next scheduler startup/tick.
- **USER VISIBILITY**: `list_runs()` shows the RECLAIMED status and the elapsed-time detail message.
- **Evidence**: **[VERIFIED-CODE]** read `scheduler/store.py::reclaim_stale_locks` in full this session (see docstring cited above); pre-existing test coverage, unmodified this session, re-confirmed passing. **Autonomous hardening cycle 8 addendum**: a related, distinct defect found via a state-machine attack on this same mechanism -- see entry #25 below.

### 12. Process crash / restart while a paper position is open

- **FAILURE**: process killed with an open paper position.
- **DETECTION**: `PaperStore` persists position state to disk on every transition, not just at shutdown.
- **SAFE RESPONSE**: on restart, the position is read back from disk exactly as it was, not lost or duplicated.
- **RECOVERY**: automatic.
- **USER VISIBILITY**: dashboard/CLI reflect the recovered state immediately.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_paper_restart.py` (pre-existing, unmodified, confirmed passing in this session's regressions). **Autonomous hardening cycle 8 addition**: `tests/failure_injection/test_paper_crash_boundary.py` closes a distinct, previously-untested boundary -- a crash DURING the fill transaction itself (before it ever commits), proving a real, uncommitted SQLite transaction rolls back completely (order still PENDING, no orphaned fill or position row, bar cursor unadvanced) via a genuine cross-connection re-read of a real temp file, then that a clean retry after the simulated crash fills exactly once with no leftover partial state.

### 13. Kill-switch state lost on restart

- **FAILURE**: an operator activates the kill switch, then the process restarts.
- **DETECTION**: N/A -- the switch state itself is the thing being checked, freshly, on every call.
- **SAFE RESPONSE**: `LiveStateStore`'s kill-switch read has zero caching -- it is read fresh from disk on every check, so a restart cannot silently "forget" an active kill switch.
- **RECOVERY**: N/A -- nothing to recover, the state was never held only in memory.
- **USER VISIBILITY**: kill-switch status is queryable at any time and reflects disk truth. **Autonomous hardening cycle 4 addition**: activating or resetting the kill switch (from any caller -- CLI or dashboard) now also emits a `logger.warning`, so the event is visible in a `--log-file`-backed log stream, not only by actively polling status. Previously this state change left zero trace in application logs at all.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_live_state_store.py:131-140` (a real restart test, confirmed present and passing, per this session's own re-verification against the current file); `tests/test_live_state_store.py::test_activate_kill_switch_logs_a_warning_with_the_reason`/`test_reset_kill_switch_logs_a_warning` (autonomous hardening cycle 4). **Autonomous hardening cycle 8 addition**: `tests/test_kill_switch_pipeline.py::test_kill_switch_survives_a_restart_and_still_blocks_a_fresh_pipeline` closes a gap in what was actually proven -- every prior pipeline-level test built the pipeline from the SAME `LiveStateStore` instance that activated the switch, within one process; this test activates the switch, closes that connection entirely, then builds a BRAND NEW `LiveStateStore` and a BRAND NEW `LiveSimPipeline` on top of it and proves the fresh pipeline still refuses to create any new order -- the persisted disk state, not an in-memory flag, is what enforces the block.

### 14. Config file missing or malformed at startup

- **FAILURE**: a required config file (risk config, scheduler config, critic config) is absent or has invalid syntax/values.
- **DETECTION**: dependent on each config loader's own validation (pydantic models raise on invalid shape where used); no single unified "config health" pre-flight check across all config sources.
- **SAFE RESPONSE**: **closed for both operator-editable config-file boundaries, autonomous hardening cycles 12-13** (`core/config.py::Settings` has no file/env-var loading at all and was re-confirmed to still have zero reachable untrusted-input path -- correctly out of scope; `risk/config.py`/`RiskConfig` is already well-guarded by `Field` constraints at every call site, confirmed in cycle 7's numeric-robustness audit, with no separate YAML-loading path to attack).
  - **Cycle 12** (`scheduler/config.py::ScheduleConfig.from_yaml_file`, via `--config`): a slot missing a required key, an unparseable time string, an unrecognized action, or a non-mapping slot entry each raised a raw, unwrapped `KeyError`/`TypeError`/`ValueError` -- AND `SchedulerConfigurationError` itself (already used for the pre-existing logical checks: inverted window, non-positive `frequency_minutes`) was missing from `main.py`'s own `_CONTROLLED_ERRORS` tuple, so even the well-designed, clear error message never reached the operator. Fixed: every slot-construction failure now raises the same typed `SchedulerConfigurationError` naming the slot's position, added to `_CONTROLLED_ERRORS`.
  - **Cycle 13** (`market_data/universe.py::MarketUniverse`, via `--watchlist-file`): three real defects, one of them the most serious found in this campaign's entire config-adversarial domain. (1) A non-string watchlist symbol (e.g. an unquoted numeric ticker) raised a raw `AttributeError`. (2) A non-dict `market_universe` YAML value raised a raw `AttributeError`. (3) **`symbols: AAPL`** (a bare scalar -- a plausible YAML typo for a one-item list) previously **SILENTLY** produced `('A', 'P', 'L')` as the universe, via `list("AAPL")` iterating the string's characters -- three garbage single-letter tickers, with **no error at all**. This is a genuine silent-data-corruption defect (a scanner could operate on a completely wrong universe undetected), not merely a crash -- the highest-severity finding in this entire domain. Fixed: symbols must now actually be a `list`/`tuple`; a non-string entry or non-dict config both raise clear, typed `ValueError`s (already covered by `main.py`'s pre-existing `ValueError` entry in `_CONTROLLED_ERRORS` -- no `main.py` change needed this time).
- **RECOVERY**: manual (operator fixes the config file).
- **USER VISIBILITY**: now clear and consistent for both audited config-file paths.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_scheduler_config.py` (6 tests, cycle 12), `tests/test_cli_schedule.py::test_a_malformed_schedule_config_file_produces_a_clean_cli_error_not_a_traceback` (cycle 12, a real `main.main()` invocation), `tests/test_market_data_universe.py` (4 new tests, cycle 13), `tests/test_cli_universe.py::test_a_malformed_watchlist_file_produces_a_clean_cli_error_not_a_traceback` (cycle 13, a real `main.main()` invocation) -- all proving the clean surface end-to-end through the actual CLI entry point, not just the isolated config loaders.

### 16. Duplicate prediction/order-intent record written twice

- **FAILURE**: a retried call or race condition (e.g. a manual `predict` CLI invocation overlapping a scheduled `daily-report` run against the same `predictions.db`) causes the same logical symbol+entry-bar prediction to be inserted twice.
- **DETECTION**: **fixed in the release-gate pass** -- `predictions/store.py` and `predictions/direction_forecast_store.py` now migrate in a real `entry_time`/`as_of` column (backfilled from each pre-existing row's own `data_json`) and attempt a genuine `UNIQUE(symbol, entry_time)`/`UNIQUE(symbol, as_of)` index at the database level, not just an application-level check.
- **SAFE RESPONSE**: `save_prediction`/`save_forecast` now raise a typed `DuplicatePredictionError`/`DuplicateForecastError` on a genuine constraint hit; both real `main.py` call sites already check `has_prediction_for_entry`/`has_forecast_for_bar` first, so this is a race backstop, not a behavior change on the normal single-writer path (confirmed: 113 prediction/forecast/tracker tests unaffected). If an already-deployed database happens to already contain duplicate rows (possible under the old app-level-only prevention), the unique index is skipped gracefully -- `duplicate_prevention_enforced_at_db_level = False` -- rather than crashing startup or deleting the pre-existing rows.
- **RECOVERY**: N/A for the constraint itself (it prevents new duplicates going forward); a database already carrying historical duplicates is not automatically deduplicated (disclosed -- see mission's own "never delete critical trading state automatically" rule).
- **USER VISIBILITY**: `duplicate_prevention_enforced_at_db_level` is queryable on the store instance; not yet surfaced through a CLI/dashboard health view (that gap remains -- see scenario/gap summary below).
- **Evidence**: **[VERIFIED-TEST]** 8 new tests across `tests/test_predictions_store.py`, `tests/test_direction_forecast_store.py`, `tests/test_core_sqlite_util.py`, including a simulated pre-migration on-disk schema and a simulated pre-existing-duplicate database exercising the graceful-degradation path.

### 18. Cache staleness silently treated as fresh

### 19. Naive/aware datetime comparison raises `TypeError: can't compare offset-naive and offset-aware datetimes`

- **FAILURE**: historically recurring (named "Phase 33/37/42" bug class in code comments) -- market-data timestamps (naive) compared against record-metadata timestamps (aware) without normalization.
- **DETECTION**: previously each of 10+ call sites reimplemented its own ad-hoc fix independently (one file, `predictions/tracker.py`, had two different implementations of the same fix).
- **SAFE RESPONSE**: **consolidated this session** into `core/timeutil.py` with an explicit, documented two-case policy (`to_naive` for market/bar data, `as_utc_aware` for record/system metadata) plus a third function (`match_index_awareness`) for the bidirectional case of matching a scalar to an existing DataFrame index's own awareness.
- **RECOVERY**: N/A -- centralizing the policy prevents a 4th independent reinvention, it does not itself recover from a live occurrence.
- **USER VISIBILITY**: would previously surface as a raw `TypeError` traceback; now governed by one tested, documented module.
- **Evidence**: **[VERIFIED-TEST]** new `tests/test_core_timeutil.py` (13 tests) plus zero-behavior-change confirmed via the full regression (1989 passed, 0 failed) across every migrated call site.

- **Evidence**: **[VERIFIED-CODE]** confirmed via reading `strategy/promotion_gate.py` and `learning/profitability.py` in this and prior sessions; unmodified (except the datetime-normalization delegation, zero behavior change) this session.

### 21. A single stored row's `data_json` is malformed or tampered with, independent of whole-file corruption

- **FAILURE**: a specific row's JSON no longer matches the Pydantic model expected to read it back -- distinct from #6 (whole-FILE corruption): the file opens fine, `PRAGMA integrity_check` reports "ok," but one row's content is bad (external tampering, or corruption isolated to that row's page).
- **DETECTION**: **autonomous hardening cycle 1/2 addition** -- every one of the 12 stores' `Model.model_validate_json(row)` read call sites now goes through `core.sqlite_util.parse_model_json()`, which raises a clear `MalformedRowError` naming the model and row identifier.
- **SAFE RESPONSE**: previously, this raised a raw `pydantic.ValidationError` (or, for the one dataclass-based store, a raw `KeyError`/`TypeError`) straight out of the store -- functionally still fail-closed (the bad read still fails rather than silently returning wrong data) but with a traceback an operator has to interpret rather than a named, actionable error.
- **RECOVERY**: manual -- the row's data is genuinely unreconstructable from what's stored; see `TROUBLESHOOTING.md`'s dedicated entry.
- **USER VISIBILITY**: the error names the model and row identifier directly, rather than requiring the operator to decode a Pydantic traceback.

### 25. A scheduler run finishes LATE, after it was already reclaimed as stale by another process (a "zombie completion")

- **FAILURE**: a slow/hung process's run genuinely exceeds `staleness_seconds` and is reclaimed (marked RECLAIMED, freeing the lock for a new run) by another process's tick -- but the original ("zombie") process was not actually dead, and eventually finishes its own work and calls `finish_run()` to report its outcome.
- **DETECTION**: **found via a real state-machine attack (autonomous hardening cycle 8), not theoretical** -- `SchedulerRunStore.finish_run()` previously had NO terminal-state guard at all, unlike every other state machine in this project (`Position`'s CLOSED, `PaperOrder`'s FILLED). A reproduced probe confirmed the zombie's late `finish_run(COMPLETED)` call silently overwrote the RECLAIMED row back to COMPLETED, with no error, no warning, nothing -- corrupting the audit trail: an operator reading `schedule status` would see a clean "completed" run with zero trace it was actually orphaned and superseded by a newer run for the same slot.
- **SAFE RESPONSE**: **fixed this cycle** -- `finish_run()` now guards its UPDATE with `WHERE status = 'RUNNING'`, checks `cursor.rowcount`, and raises a new, dedicated `InvalidRunTransitionError` if the run is no longer RUNNING (already RECLAIMED, COMPLETED, or FAILED). `scheduler/runner.py::run_tick` catches this specific error on both its success and failure paths, returning a clear `TickResult` explaining what happened rather than crashing the tick or silently corrupting the record.
- **RECOVERY**: N/A for the zombie run itself (its late outcome is simply not recorded, by design); the newer, real run for that slot is completely unaffected and continues normally.
- **USER VISIBILITY**: the reclaimed run's audit-trail entry stays honestly RECLAIMED; the zombie's late attempt is silently (but safely) discarded rather than corrupting the record.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_scheduler_store.py` (3 new tests: reclaimed-then-zombie-finish, already-completed, already-failed), `tests/test_scheduler_runner.py` (2 new tests proving `run_tick` itself handles being reclaimed mid-flight gracefully on both the success and failure paths, via deterministic injection -- reclaiming the run's own lock from inside a monkeypatched `_execute_slot`).
- **Scope note, honestly disclosed**: this fix closes the RECORD-KEEPING corruption (a reclaimed run's audit trail can no longer be silently overwritten to look like a clean success). It does NOT, and cannot by itself, prevent a genuinely-still-alive zombie process's own APPLICATION-level side effects (e.g. a `shadow-run --paper-execute` submitting a paper order) from having already occurred concurrently with a newer run for the same slot -- fully preventing that would require OS-level process ownership tracking (e.g. distributed locks with fencing tokens), a materially different architecture than this project's single-machine, SQLite-backed design. `staleness_seconds`'s own default (1800s) remains a deliberately conservative, probabilistic choice for this reason.

### 28. Two independent processes submit the IDENTICAL signal at the same instant (a real concurrency race)

- **FAILURE**: two separate callers -- e.g. a manually-triggered `shadow-run --paper-execute` racing an independent scheduler tick, or two concurrent MCP `paper_trade_signal_tool` calls -- both call `PaperTradingEngine.submit_signal()` with the identical `Signal` (same `stable_id()`) at genuinely the same instant, each from its own SQLite connection.
- **DETECTION**: **found via a real, genuinely-reproduced multi-threaded concurrency test, autonomous hardening cycle 15** (not theoretical) -- `submit_signal()`'s own "does a journal entry already exist" check (`find_journal_entry_by_signal_id`) and the transaction that inserts a NEW signal/journal are two separate, non-atomic steps: a classic check-then-act TOCTOU. - **SAFE RESPONSE**: **fixed this cycle** -- the DB-level `signals.signal_id` `PRIMARY KEY` and `journal_entries.signal_id` `UNIQUE` constraint already prevented an actual DUPLICATE ROW from ever being created (that half of the idempotency contract always held), but the LOSER of the race previously got a raw crash instead of this method's own documented "the existing result is returned unchanged" behavior. `submit_signal()` now catches `sqlite3.IntegrityError` from the insert attempt and, on catching it, re-reads and returns the WINNER's own already-committed `JournalEntry` -- exactly the idempotent behavior the docstring always promised, now genuinely true under real concurrent contention, not just sequential/single-threaded calls.
- **RECOVERY**: N/A -- both callers now correctly observe and return the SAME single result; no manual intervention, no orphaned state.
- **USER VISIBILITY**: no crash surfaces to either caller; both receive the identical, correct `JournalEntry`.
- **Evidence**: **[VERIFIED-TEST]** `tests/test_paper_engine.py::test_submit_signal_is_idempotent_under_real_concurrent_contention` (real threads, real temp SQLite file, a `threading.Barrier` forcing genuine overlap, run across the fix confirming both threads agree on the same journal entry and exactly one row exists) plus `test_submit_signal_is_idempotent_sequentially` (the simpler same-thread case, previously untested in this file despite the docstring's own claim).
- **Adjacent concurrency surface investigated, not a gap**: the `account` table's single-row upsert (`id INTEGER PRIMARY KEY CHECK (id = 1)`, `INSERT ... ### 29. Unbounded in-memory queue in the Dhan live-feed source (resource exhaustion, closed)

- **FAILURE**: `live/dhan/market_data_source.py::DhanMarketDataSource._bar_queue` was a plain `queue.Queue()` with no `maxsize` -- every completed candle from the WebSocket's own background thread was `put()` onto it unconditionally (`_handle_packet`), and only removed by the consumer calling `next_bar()`. If the consumer fell behind the feed for an extended period -- most plausibly `paper-live`'s own interactive human-approval prompt blocking for a long time while the market keeps ticking -- completed-but-unconsumed `MarketBarEvent`s would accumulate on this queue with no upper bound.
- **DETECTION**: found via resource-exhaustion auditing, autonomous hardening cycle 16 (a codebase-wide search for unbounded `list`/`queue`/`dict` growth in every real, in-process-long-lived data structure). Confirmed by direct code reading (`queue.Queue()` at construction, `put()` at the wire-handling call site, no size check anywhere).
- **SAFE RESPONSE**: **fixed, autonomous hardening cycle 21**. `_bar_queue` is now `queue.Queue(maxsize=max_queued_bars)` (new dataclass field, default 2000 -- deliberately generous for this project's actual deployment scale; a hard backstop, not a normal-operation throttle). The wire-handling call site (`_handle_packet`) now goes through a new `_enqueue_bar()` method that uses `put_nowait()` -- NEVER a blocking `put()`, which would stall the WebSocket library's own background receive thread (missed pings, connection instability) -- and on `queue.Full`, evicts the OLDEST queued bar via `get_nowait()` (catching `queue.Empty` defensively for the narrow window where the consumer's own `get()` might have just drained it first) before retrying the `put_nowait()`, logging a `warning` naming the dropped event's symbol. Drop-oldest is the deliberately-chosen policy for LIVE data: a consumer that has fallen this far behind needs the most recent state once it catches up, not an ever-growing backlog of stale history to process bar-by-bar regardless.
- **RECOVERY**: automatic and continuous -- the feed keeps accepting new bars and self-corrects once the consumer catches up; no manual intervention, no crash.
- **USER VISIBILITY**: a `logger.warning` naming the dropped bar's symbol each time an eviction occurs; no dedicated metric/health-check surfaces queue depth (left as a genuinely low-value addition -- see below).
- **Evidence**: **[VERIFIED-TEST]** -- five new deterministic tests in `tests/test_dhan_market_data_source.py` (via direct `_handle_packet()` calls, no real network, matching this file's own established testing convention): the queue never exceeds `max_queued_bars` even when the consumer never drains it; `put_nowait()` never blocks or raises once already full; overflow drops the OLDEST bar, not the newest (verified by asserting the exact surviving bar sequence); overflow logs a warning naming the dropped bar's symbol (`caplog`); and a consumer that keeps up (drains via `next_bar()` as bars complete) never triggers a single drop or warning. Full existing 37-test suite for this module re-run with zero regressions (42 passed total, including the 5 new tests).
- **Process note**: the fix deliberately used `put_nowait()` + drop-oldest rather than the naive `queue.Queue(maxsize=N)` + default blocking `put()`, because the latter would have traded an unbounded-memory-growth risk for a WORSE failure mode (a stalled WebSocket receive thread) -- exactly the risk this entry originally disclosed as the reason NOT to rush a naive fix in cycle 16. This mirrors the same "disclose now, fix later with room for careful design and verification" judgment this campaign already made once for this same file's CONNECTING-timeout gap (cycle 7 disclosed it, cycle 8 closed it after a structured re-audit).
- **Other resource-exhaustion surfaces checked in cycle 16, found already bounded (negative audits)**: log growth (`core/logging.py`'s `RotatingFileHandler`, 10MB x 5 backups, already bounded); retry loops (`market_data/resilience.py`'s `RetryPolicy.max_attempts`, the Dhan reconnect's `max_reconnect_attempts`, both already bounded); `live/pipeline.py`'s `pending_approvals` dict (entries are explicitly `del`eted once a decision is reached -- bounded by the naturally-small number of CURRENTLY pending signals, not accumulating forever across a long session); `dashboard/app.py`'s per-request lists and its one persistent module-level cache (`_cached_holidays`, a single value, not a growing collection); `paper/advance.py`'s hold-back/retry mechanism (no internal loop at all -- bounded by the external scheduler-tick cadence that invokes it). Database row growth itself remains a deliberate, already-disclosed accepted limitation (see the closing summary below) -- no automatic retention/archival policy, intentionally, since these rows are exactly the "critical trading state" this project's own rule forbids automatically deleting.

The original concurrent-thread test also still passes, now consistently. Full `live/`-suite regression (134 tests across `test_live_pipeline.py`, `test_live_state_store.py`, `test_live_workstation.py`, `test_kill_switch_pipeline.py`, `test_mcp_live_workstation.py`, `test_dashboard_intelligence.py`, `test_paper_advance.py`) confirmed no behavioral regression from the restructuring.

Never remove a failing test to force green." The cycle-19 test was never weakened to accommodate the incomplete first fix; it was trusted, and it was right.
- **Negative audit, autonomous hardening cycle 23**: the SAME CAS mechanism was directly, executably attacked from a different angle -- `approve_pending()` racing `expire_pending_approvals()` (rather than `reject_pending()`) across two independently-restored `LiveSimPipeline` instances (simulating a restart), with a deliberately tiny `approval_timeout_seconds` plus a real sleep so the signal is GENUINELY expired by real wall-clock time before either thread races. ### 31. A stale bar could still fill an already-pending order or close an open position

- **FAILURE**: `live/pipeline.py::process_next` computed its own `FreshnessPolicy` check (`STALE_SIGNAL_SUPPRESSED`) *after* already calling `PaperTradingEngine.process_bar()` -- but `process_bar` is what fills any PENDING order at the current bar's open, and checks any OPEN position's stop/target against it. The staleness check that ran afterward only ever suppressed generating a *new* signal from that specific bar; it never stopped an entry fill or exit already in flight from completing on data the pipeline itself was about to judge too stale to trust. Concretely: a signal generated on a genuinely fresh bar N gets risk-approved into a PENDING order; the market data feed then falls behind (a Dhan reconnect stall, or exactly cycle 21's own bounded-queue backlog scenario) before the NEXT bar N+1 -- the one that actually fills that order -- is delivered. By the time N+1 arrives and is processed, it may be well past the freshness threshold, yet the fill happened anyway, unconditionally, before the staleness check ever ran. A direct violation of this project's own unconditional "STALE MARKET DATA -> NO TRADE" invariant -- the invariant names no carve-out for "unless a prior bar already authorized it."
- **DETECTION**: found via autonomous hardening cycle 22's cross-component/time-dimension adversarial audit -- tracing the full market-data -> freshness -> paper-execution boundary rather than re-auditing any single component in isolation. Confirmed by direct code reading (the freshness check's position in `process_next`, relative to `engine.process_bar`'s call) and then reproduced executably (see Evidence below) -- not merely theoretical.
- **SAFE RESPONSE**: **fixed, autonomous hardening cycle 22**. `PaperTradingEngine.process_bar` gained a new `is_fresh: bool = True` parameter (default `True` so every non-live caller -- backtest replay via `paper/replay.py`, `paper/advance.py`'s catch-up fills, `mcp_server/server.py`, and the dozens of existing direct-call tests -- is completely unaffected; "freshness relative to wall-clock now" is a live-pipeline-only concept, meaningless for replayed historical data). `live/pipeline.py::process_next` now computes its `FreshnessPolicy` check *before* calling `process_bar` (the computation itself is unchanged -- still `bar.timestamp` vs `now` -- only *when* it runs moved) and threads the result through as `is_fresh`. When `is_fresh=False`, `process_bar` still runs its existing dedup/out-of-order bookkeeping (`last_bar_timestamp`, `roll_to_day`, `save_account`) exactly as before -- only the position-affecting block (`_fill_pending_order`/`_process_open_position`) is skipped, returning a new `BarOutcome.STALE_SKIPPED`. The skipped action is not lost, only deferred: the same still-PENDING order or still-OPEN position is re-evaluated against the next bar that arrives, fresh or not.
- **RECOVERY**: automatic -- as soon as a subsequently-arriving bar passes the freshness check, the deferred fill/exit check runs normally against it.
- **USER VISIBILITY**: `PipelineStepResult.kind == "STALE_SIGNAL_SUPPRESSED"` (unchanged, pre-existing outcome value) now genuinely means "no trade action of any kind was taken this bar," not merely "no new signal was generated."
- **Evidence**: **[VERIFIED-TEST]**, at two levels. Full existing `tests/test_paper_bar_ordering.py` + `tests/test_live_pipeline.py` suites (36 tests) re-run with zero regressions, plus the broader `paper/`+`live/`+MCP consumer suite.

### 32. A duplicate or out-of-order bar silently polluted the indicator history

- **FAILURE**: `live/pipeline.py::process_next` called `buffer.append(bar)` (accumulating the bar into the per-symbol `_SymbolBuffer` that `to_indicator_series()` later turns into the DataFrame `generate_signal()` reads) UNCONDITIONALLY, before ever checking whether `PaperTradingEngine.process_bar()` was about to reject that same bar as `DUPLICATE_SKIPPED` or raise `OutOfOrderBarError`. The EXECUTION layer's own dedup/ordering guarantees (Phase 7A, extensively tested) were completely correct and unaffected -- no double fill, no silently-reordered trade history. But the SEPARATE indicator-history buffer had no such gate at all: a duplicate bar was appended a second time (an extra, redundant row); an out-of-order bar was appended out of chronological position (a genuinely misplaced row). `OHLCV.to_dataframe()` builds its `DatetimeIndex` from list order with no sort, and the rolling/ewm functions `compute_indicator_series()` uses (SMA/RSI/ATR/MACD) operate on row POSITION, not the index value -- so either case silently skews every subsequent indicator computed from that buffer for the rest of the session, which then feeds `strategy.generate_signal()` directly. A "silent incorrect decision" class defect: nothing crashed, nothing was flagged, the corrupted indicators simply fed the strategy quietly.
- **DETECTION**: found via autonomous hardening cycle 23's cross-component audit of the SAME code path cycle 22 had just modified (market data -> buffer -> indicators -> signal generation), specifically asking "does the execution layer's own well-tested dedup/ordering guarantee also cover every OTHER consumer of this same bar?" -- not by re-testing `process_bar`'s own dedup in isolation (already thoroughly covered) but by tracing where else the SAME bar object flows.
- **SAFE RESPONSE**: **fixed, autonomous hardening cycle 23**. `buffer.append(bar)` moved to occur only AFTER `process_bar()` returns/raises -- specifically, only for a bar that is neither `DUPLICATE_SKIPPED` nor an `OutOfOrderBarError`. A STALE bar (freshness-suppressed) is still appended -- its data is real, chronologically-ordered market data, just arriving late; only ITS signal-generation consequence is suppressed (matching cycle 22's own "stale != corrupt" distinction, an intentional asymmetry, not an oversight). `state_store.save_feed_status()` remains unconditional (still correctly diagnostic-only, unaffected by this fix).
- **RECOVERY**: N/A -- the corruption is prevented from occurring at all, not detected and repaired after the fact.
- **USER VISIBILITY**: none needed -- the indicator series is now simply correct.
- **Evidence**: **[VERIFIED-TEST]**. Two existing tests (`test_duplicate_bar_is_a_no_op_via_the_pipeline`, `test_out_of_order_bar_is_rejected_not_silently_applied`) extended with a direct assertion on `pipeline._buffers["TEST"].bars` (proving the rejected bar contributed zero entries), plus a new end-to-end test (`test_duplicate_and_out_of_order_bars_never_pollute_the_indicator_series`) asserting the actual `to_indicator_series()` DataFrame output -- exact row count and chronological index -- after a script deliberately interleaving a duplicate and an out-of-order delivery among three genuine bars. **Mutation-tested**: all 3 tests confirmed to FAIL when the old unconditional early `buffer.append(bar)` call was temporarily reintroduced, before being confirmed to pass against the real fix.

### 33. A PENDING order could fill (and an approved circuit-breaker bypass) after the kill switch or a risk circuit breaker activated mid-flight -- CRITICAL

- **FAILURE**: a signal risk-approved while the account was healthy (and the kill switch inactive) creates a `PaperOrder` with `status=PENDING`; the actual FILL happens later, whenever the next bar arrives and `PaperTradingEngine.process_bar()` runs. In `live/pipeline.py::process_next`, `process_bar()` was called UNCONDITIONALLY -- with no re-check of the kill switch or any account-level circuit breaker (`max_drawdown_pct`/`max_daily_loss_pct`/`consecutive_loss_hard_limit`) immediately beforehand. The pipeline's own `is_kill_switch_active()` check exists, but runs LATER, and only gates generating a brand-NEW signal FROM the current bar -- it never protected an entry already in flight from a PRIOR bar's decision. Concretely: a signal approved at T0 creates a PENDING order; the kill switch is activated at T1 (a human hits the emergency stop); the next live bar arrives at T2 and fills the order anyway, because `process_bar()` (which performs the fill) runs BEFORE the pipeline's kill-switch check, and that check does not gate `process_bar()` at all. The exact same exposure exists for the account circuit breakers: an order approved while the account was healthy could fill after the account has since crossed a drawdown/daily-loss/consecutive-loss limit via a completely DIFFERENT symbol's trades. This is a direct violation of two of this project's own sacred, never-weaken invariants simultaneously: "PERSISTENT KILL SWITCH -> NO TRADE" and the account-level circuit breakers `risk/engine.py::account_level_halt_reasons()` exists specifically to enforce.
- **DETECTION**: found via autonomous hardening cycle 24's "alternate authorization paths" attack (mission step 5: "can another path authorize the same action without this veto?"), triggered by noticing that `paper/advance.py` ALREADY carries an explicit, well-documented guard for exactly this defect class at ITS OWN call site (its own docstring: "Real, reproduced finding... an account driven past max_drawdown_pct via a different symbol's repeated stop-outs correctly REJECTED a fresh signal, yet a symbol's OLD, already-approved PENDING order... filled anyway once its turn came") -- prompting the question "does `live/pipeline.py`, the ACTUAL continuous live path, carry the equivalent guard?" It did not.
- **SAFE RESPONSE**: **fixed, autonomous hardening cycle 24**. Mirrors `paper/advance.py`'s own pattern exactly. `PaperTradingEngine.process_bar` gained a new `allow_new_fill: bool = True` parameter (default True, so every non-live caller -- backtest replay, `paper/advance.py`'s own already-guarded call site, direct tests -- is completely unaffected). When `False`, the fill-a-PENDING-order branch is skipped entirely (returning the new `BarOutcome.EXECUTION_HALTED_SKIPPED`); the order remains PENDING, re-evaluated against the next bar. Deliberately does NOT affect an already-OPEN position's stop/target check -- that branch runs unconditionally regardless of this flag, the same distinction `paper/advance.py`'s own docstring draws ("a symbol that already HAS an open position... must still be monitored... regardless of an account-level halt" -- refusing to manage an existing position during a halt/kill-switch event would strand it with no way to exit, a worse, new bug). `live/pipeline.py::process_next` now computes `allow_new_fill` immediately before calling `process_bar` -- `False` only when there is no open position yet for the symbol AND (`account_level_halt_reasons()` is non-empty OR the kill switch is active) -- and surfaces a new `PipelineStepResult.kind == "PENDING_FILL_HALTED"` when a fill was actually skipped this way.
- **RECOVERY**: automatic -- the deferred fill is re-evaluated against the next bar, once the halt condition clears.
- **USER VISIBILITY**: `PipelineStepResult.kind == "PENDING_FILL_HALTED"`, a new, explicit outcome distinct from the pre-existing `KILL_SWITCH_ACTIVE` (which still fires separately for a brand-new signal on the same bar, when applicable).
- **Evidence**: **[VERIFIED-TEST]**, at two levels. Unit level (`tests/test_paper_bar_ordering.py`, 3 new tests): `allow_new_fill=False` never fills a pending order; NEVER blocks an already-open position's stop/target check (the critical asymmetry); the omitted default remains byte-for-byte pre-cycle-24 behavior. End-to-end level (`tests/test_live_pipeline.py`, 3 new tests, real `LiveSimPipeline`/`PaperStore`/`LiveStateStore`, no mocks): a pending order never fills after the kill switch activates mid-flight; a pending order never fills after the account crosses the default 10% drawdown circuit breaker (simulated via direct account mutation, exactly mirroring how a DIFFERENT symbol's real losses would have moved it); an already-OPEN position's stop is STILL checked and closes correctly despite an active kill switch. **Mutation-tested**: all 3 core new tests confirmed to FAIL when `allow_new_fill`'s guard was temporarily forced to always-true, before being confirmed to pass against the real fix -- the kill-switch mutant test additionally revealed the EXACT mechanism of the original bug: the mutated code returned `kind="KILL_SWITCH_ACTIVE"` (from the separate, pre-existing, correct check on a NEW signal), which superficially looks like "nothing happened," while the PENDING order had ALREADY silently filled moments earlier inside `process_bar()`.
- **Sacred-file note**: the third `live/pipeline.py` change this campaign has made to a sacred file, reviewed line-by-line -- purely additive (a new computed `allow_new_fill` value threaded into an existing call, plus one new early-return branch); 7 of the 8 sacred files remain zero-diff this cycle.
- **Severity classification**: CRITICAL, not merely HIGH -- of every defect this campaign has found and fixed, this is the one that most directly touches BOTH of the two most safety-critical invariants at once (kill switch AND risk circuit breakers) in the actual continuous live-trading path, not a batch/backtest-only path.

### 34. A TOCTOU window let approve_pending() fill an order after the kill switch activated between the CAS claim and submit_signal() -- CRITICAL

- **FAILURE**: `LiveSimPipeline.approve_pending()` checked `is_kill_switch_active()` exactly ONCE, inside `_check_actionable()`, at the very TOP of the method -- before the cycle-20 CAS claim write (`LiveStateStore.update_decision`) and before `submit_signal()` (the call that actually creates the real `PaperOrder`). `RiskEngine.evaluate()` -- the method's own "mandatory second risk check" -- has NO kill-switch awareness at all: verified directly against `risk/engine.py`'s complete source during cycle 24's mutation audit, kill switch is a live-system-only concept living in `LiveStateStore`, deliberately kept out of the pure, deterministic, backtest-reusable `RiskEngine`. So a kill switch activated in the window between the initial check and `submit_signal()` actually running -- e.g. a human hits the emergency stop in the exact moment between clicking Approve and the call reaching `submit_signal()` -- was never caught by anything, and the order was created anyway.
- **DETECTION**: found via autonomous hardening cycle 25's temporal-authorization attack (mission directive: "a previously valid HUMAN_APPROVED decision must NOT become an execution authorization that survives later kill-switch activation") -- tracing `approve_pending()`'s exact sequence (CAS claim -> account/risk read -> `submit_signal()` -> execution) rather than re-testing the CAS mechanism itself (already proven correct for approve-vs-reject and approve-vs-expire in cycles 19/20/23) against a DIFFERENT condition that changes over the same window: the kill switch.
- **SAFE RESPONSE**: **fixed, autonomous hardening cycle 25**. A second `is_kill_switch_active()` check now runs immediately after the CAS claim succeeds (this call holds exclusive ownership of `signal_id` at that point) and immediately before `submit_signal()` is called. If the kill switch is active, the lifecycle transitions `HUMAN_APPROVED -> RISK_REJECTED` (already a legal transition, reused rather than adding a new state), `submit_signal()` is never called, `finalize_decision()` records `final_execution_result="KILL_SWITCH_ACTIVE"`, and the caller receives `ApprovalActionOutcome.KILL_SWITCH_ACTIVE`. This collapses the previously-unbounded window (an entire SQLite CAS write plus everything up to `submit_signal()`) down to the single line between the new check and the `submit_signal()` call -- the same residual-window pattern every other kill-switch check in this codebase already accepts (e.g. `process_next()`'s own pre-existing check before `_handle_signal`), not a claim of perfect zero-window atomicity, which would require a larger architectural change (a shared-transaction read) not used anywhere else in this project's kill-switch handling.
- **RECOVERY**: N/A -- the losing decision is recorded as a real, final `RISK_REJECTED` outcome, not silently dropped or left ambiguous.
- **USER VISIBILITY**: `ApprovalActionResult.outcome == "KILL_SWITCH_ACTIVE"`; persisted record shows `state=RISK_REJECTED`, `final_execution_result="KILL_SWITCH_ACTIVE"`.
- **Evidence**: **[VERIFIED-TEST] [VERIFIED-MUTATION] [VERIFIED-CONCURRENCY]**. Two new tests in `tests/test_approval_security.py`. (1) A deterministic proof (mirroring cycle 20's own technique, not timing-dependent): `LiveStateStore.update_decision` is wrapped so the kill switch activates the INSTANT the CAS claim commits, before `approve_pending`'s own next line runs; asserts `submit_signal` (a `MagicMock` configured to raise if called) is never reached, no `PaperOrder` is created, and the persisted record lands on `RISK_REJECTED`/`KILL_SWITCH_ACTIVE`. (2) A REAL two-thread confirmation using a genuinely separate `LiveStateStore` connection (a different process/thread), synchronized with a `threading.Event` pair so the main thread's approval BLOCKS until the activator thread's OWN connection has actually committed the write -- the first version of this test (a plain one-directional signal) raced and mostly showed `APPROVED` (the activator's own connection-open overhead meant it usually lost), which was itself instructive: it proved the residual window is real and physically necessary against a genuinely uncoordinated writer, not evidence of a defect in the fix; the corrected two-way-synchronized version forces the intended interleaving and confirms `KILL_SWITCH_ACTIVE` with no order created, stable across 5 repeated runs. **Mutation-tested**: both tests confirmed to FAIL (one asserting `APPROVED` instead of `KILL_SWITCH_ACTIVE`, the mock's `assert_not_called()` firing) when the new check was disabled, before confirming they pass against the real fix.
- **Sacred-file note**: the fourth `live/pipeline.py` change this campaign has made to a sacred file, reviewed line-by-line -- a single new early-return branch inserted between the existing CAS-claim block and the existing `submit_signal()` call, nothing else touched; 7 of 8 sacred files remain zero-diff this cycle.
- **Process note**: the FIRST version of the real-thread concurrency test was itself a subtle test-construction defect (a one-directional `threading.Event` that let the two threads merely race rather than forcing the intended interleaving) -- caught by its own failing assertion, not assumed correct because "it uses real threads." Fixed by adding a second event so the main thread genuinely blocks on the activator's completion, consistent with this campaign's standing discipline of never weakening a test (or its own interpretation of a result) to manufacture green.

### 35. A crash between approve_pending()'s CAS claim and finalize_decision() left the decision permanently orphaned, unreconciled

- **FAILURE**: `approve_pending()`'s own two-phase sequence (CAS claim via `update_decision`, cycle 20; then `submit_signal()`; then `finalize_decision()`) has no crash recovery for the window between the claim committing and `finalize_decision()` running. If the process dies in that window, the persisted `pending_approvals` row is left stuck at `state='HUMAN_APPROVED'` forever. `LiveStateStore.list_pending()` deliberately queries only `state='PENDING_HUMAN_APPROVAL'` (a decided row is not "still pending" -- correct, and this IS the mechanism that prevents the orphan from ever being re-approved into a SECOND execution attempt), so nothing automatically re-runs `approve_pending()` on it -- genuinely safe from duplicate execution -- but nothing reconciled the row either: it was simply invisible and unexplainable, forever, with no operator-visible signal that anything had gone wrong.
- **DETECTION**: found via autonomous hardening cycle 26's crash-boundary campaign (mission directive: "the most dangerous scenario is execution succeeds, process dies before finalization, restart, recovery -- prove whether a second execution can occur"). Confirmed the duplicate-execution risk does NOT exist (a real, valuable negative-audit result in its own right, since `list_pending()`'s own filter already structurally prevents it) -- but tracing what DOES happen to the orphaned row surfaced this separate, genuine gap: an ambiguous-looking but actually FULLY DETERMINABLE outcome (`PaperTradingEngine._submit_signal_transaction` is one atomic SQLite transaction -- a partial commit is not possible, so whether it committed is always knowable by checking for a `JournalEntry`) was never actually checked or recorded.
- **SAFE RESPONSE**: **fixed, autonomous hardening cycle 26**. New `LiveStateStore.list_orphaned_claims()` (rows at `state='HUMAN_APPROVED'`) and `LiveSimPipeline._reconcile_orphaned_claims()`, called automatically at the end of every pipeline `__init__` (immediately after `_restore_pending_approvals()`), mirroring the scheduler's own cycle-8 `reclaim_stale_locks` precedent for automatic startup reconciliation. For each orphan: if a `JournalEntry` for that `signal_id` already exists, `submit_signal()` DID commit before the crash -- this is pure bookkeeping catch-up, recording the outcome that already, provably happened (`finalize_decision()` called with the REAL outcome, `submit_signal()` is NEVER called again). If no `JournalEntry` exists, `submit_signal()` never committed -- the orphan is marked a real, final `RISK_REJECTED` outcome (`final_execution_result="ORPHANED_CLAIM_ABANDONED_AFTER_CRASH_NO_ORDER_CREATED"`) and is **never automatically resumed into a fresh execution attempt** -- this project's own standing rule, explicit in this cycle's own mission ("Do NOT assume a persisted HUMAN_APPROVED state is safe to replay"), is honored literally: a genuinely new signal and a fresh human Approve are required if the trade is still wanted.
- **RECOVERY**: automatic, at every pipeline startup -- no manual operator intervention required for the common case (crash after successful execution: pure bookkeeping catch-up); the rare case (crash before execution) is marked abandoned, not silently stuck.
- **USER VISIBILITY**: the persisted record's `state`/`final_execution_result` now always reflects the true, final outcome instead of staying stuck at `HUMAN_APPROVED` forever; `approve_pending()` called again on the same `signal_id` returns `ALREADY_DECIDED` (the reconciled lifecycle is known, not unknown) rather than silently doing nothing or erroring.
- **Evidence**: **[VERIFIED-TEST] [VERIFIED-MUTATION]**. Two new tests in `tests/test_approval_security.py`, both against real temp SQLite files (`LiveStateStore` + `PaperStore`), simulating the crash boundary by direct SQL (moving the persisted row to `HUMAN_APPROVED`, exactly cycle 20's own precedent for simulating this class of point) then building a genuinely fresh `LiveSimPipeline` (new engine, new state store, same files -- a real restart). (1) `submit_signal()` called directly before the simulated crash (a real `PaperOrder`+`JournalEntry` committed) -- the fresh pipeline's own `__init__` reconciles it to `EXECUTED`, exactly one journal entry/order exists afterward (never duplicated). (2) No `submit_signal()` call before the simulated crash -- the fresh pipeline marks it `RISK_REJECTED`/abandoned, `approve_pending()` on it afterward still returns `ALREADY_DECIDED` (never re-executes), zero journal entries/orders exist. **Mutation-tested**: both tests confirmed to FAIL (both landing on `NOT_FOUND` instead of the reconciled `ALREADY_DECIDED`/real state) when the `_reconcile_orphaned_claims()` call was disabled, before confirming they pass against the real fix.
- **Idempotency guarantee established by this cycle**: for one logical execution identity (`Signal.stable_id()`), this architecture provides **effectively-once** execution -- at most one `PaperOrder`/`JournalEntry` is ever created, proven under: concurrent approve/reject (cycle 19/20), concurrent approve/expire (cycle 23), kill-switch-during-approve (cycle 25), and now crash-before-or-after-execution-but-before-finalization (this cycle). The ambiguous-looking case (crash mid-approval) is NOT actually ambiguous at the data level -- `submit_signal()`'s own transaction atomicity makes the true outcome always determinable -- so no external idempotency key or manual reconciliation tool is needed beyond the automatic startup reconciliation this cycle adds.
- **Sacred-file note**: `live/state_store.py` and `live/pipeline.py`'s `__init__`/new-method additions are purely additive (a new method, a new call site, zero existing behavior changed); `live/pipeline.py` is one of the 8 sacred files (fifth change this campaign has made to it), reviewed line-by-line; 7 of 8 sacred files remain zero-diff this cycle.
